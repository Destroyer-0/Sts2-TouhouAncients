## 十一、格式规则速查

| 规则 | 说明 |
|------|------|
| 富文本标记 | 原样保留 `[gold]` `[purple]` `[red]` `[green]` `[blue]` `[pink]` `[b]` 等 |
| 动画标记 | 原样保留 `[jitter]` `[sine]` `[fade_in]` 等 |
| 动态变量 | 原样保留 `{Damage}` `{Block}` `{Energy:energyIcons()}` 等 |
| 图标 | 原样保留 `{singleStarIcon}` `{energyPrefix:energyIcons(1)}` 等 |
| 标点 | 中文句号 `。` → `.`，中文逗号 `、` → `,` |
| 换行符 | `\n` 保留不变 |
| 中文名优先 | 以 `zhs/` 中的中文文本为准翻译，而非键名/类名 |
| 序数词 | 英文序数后缀**直接硬编码**（`1st` / `2nd` / `3rd` / `4th`…），与原版 STS2 一致 |

### 序数词后缀

原版 STS2 的序数词全部是**硬编码**（`BRILLIANT_SCARF` 的 `5th`、`CANDELABRA` 的 `2nd`、`PEN_NIB` 的 `10th`），因为对应数值都是固定常量。本项目沿用同一做法。

**不要**用 `{Var:choose(...)}` 动态生成序数后缀：英文序数规则依赖末两位（11/12/13 用 `th`，21/22/23 用 `st/nd/rd`），有限枚举无法覆盖 41/42/43 等，会落到默认值产生 `41th` 这类错误。

> 例：`SINISTER_PACT_DREAM` 的 `{ShopIndex}` 在源码中恒为 `1`（`CanonicalVars` 里 `new DynamicVar("ShopIndex", 1)`，全仓库无其他赋值点），故直接写 `[blue]1st[/blue]`。

## 二十三、插入位置约定（2026-10-15）

**`eng/` / `jpn/` 新增键的位置一律对齐 `zhs/` 的相对位置**——同一 key 在 zhs 中排在谁后面，就在 eng / jpn 中排在同一 key 后面；**不按字母序另行插入**。

- 理由：翻译是逐批 diff `zhs` ↔ `eng` 生成的，三者键序一致时，每一批新增内容在三个文件里落成同一块，diff 集中、便于逐条核对；按字母序插入会把同一批内容拆到不相邻的多处。
- 本批次实例：`badges.json` 的三条徽章集中排在 `THREE_SNAKE` 与 `TOO_MUCH_SATORI` 之间（曾按 `eng/badges.json` 原有字母序拆成三处，已修正）；`cards.json` 的 `LUCKY_TRICK`、`powers.json` 的 `TRICKSTER_POWER` / `LUCKY_TRICK_COUNT_POWER`、`monsters.json` 的 `INABA_TEWI_MONSTER` 整块、`relics.json` 的 `eventDescription`、`ancients.json` 的 `fight.title` 均落在 zhs 的同一相对位置。
- 核对方法：取新键在 zhs / eng / jpn 中的前一条键，三者相同即为对齐。
- 已知的既有顺序漂移（更早批次造成，本批次未动，可按需统一）：`monsters.json`（`SAIGYOUJI` 与 `MEDICINE` 的分组顺序）、`powers.json`（`GLOWING_BAMBOO`）、`relics.json`（`OBLIVION_FRAGMENT`）、`ancients.json`、`cards.json`。
