>
> **不准擅自回答用户从未提出的问题**：只回应用户明确提出的请求，不自问自答，不解释用户没问的东西。
>
> 以上两条为硬性约束，违反即视为错误行为。
>
> **严禁操作 Git**：绝对禁止在未经用户明确允许的情况下执行任何 git 操作，包括但不限于 `git reset`、`git checkout`、`git stash`、`git add`、`git commit`、`git push`、`git merge`、`git rebase`。不可操作暂存区或任何涉及 git 历史、索引的行为。此禁令优先级最高。

## 1. 目录结构

仓库根即 Godot 工程。C# 源码在 `scripts/`，本地化在 `TouhouAncients/localization/`，Godot 资源在 `images/`、`scenes/`、`shaders/`、`debug_audio/`。

```
Sts2-TouhouAncients/
├── scripts/
│   ├── Entry.cs                         # Mod 入口：Harmony.PatchAll、EncounterBgm、挑战奖励 Hook
│   ├── TouhouAncientsConfig.cs          # SimpleModConfig：强制/禁用 Ancient、运行期同步字段
│   ├── AncientRunSavedData.cs           # 开局局内数据：强制/禁用 Ancient 的主机提交与包尾同步
│   ├── AncientSpeakerProfile.cs         # 多说话者立绘/气泡配置（建议日后挪到 ancients/）
│   ├── AncientSpeakerRegistry.cs
│   ├── EncounterBgm.cs                  # 挑战战斗 mp3 BGM（建议日后挪到 encounters/）
│   ├── ancients/                        # 先古之民，命名空间目前是 TouhouAncients.Scripts
│   ├── relics/{角色}/                   # 遗物，按角色分子目录
│   ├── cards/                           # 卡牌（平铺）
│   ├── Enchantment/                     # 附魔（平铺）
│   ├── powers/                          # Power（平铺）
│   ├── potions/                         # 药水
│   ├── Afflictions/                     # 侵蚀
│   ├── monsters/                        # 挑战怪物
│   ├── encounters/                      # 挑战遭遇
│   ├── Hooks/                           # 本 Mod 补充的战斗钩子（获得能量后等）
│   ├── Patches/                         # 跨系统 Harmony 补丁
│   ├── CmdUtils/                        # 路径检查、自定义命令
│   └── keywords/                        # 自定义 CardKeyword（命名空间却是 cardTags）
├── TouhouAncients/localization/{zhs,eng,jpn}/
├── images/                              # 图标、卡肖像、立绘、精灵
├── scenes/                              # 事件背景、怪物视觉、遭遇、UI
├── shaders/
├── debug_audio/                         # 挑战战斗 BGM（mp3）

├── TouhouAncients.csproj
```

#### 第一幕（Act 1）先古之民

本 Mod 支持第一幕先古之民，与涅奥同池均匀抽取（各占 `1/(N+1)`，N 为该幕自定义先古之民数）。

- **为什么需要专门处理**：BaseLib 的 `AddCustomAncientsToPool`（Prefix 于 `ActModel.GenerateRooms`）
  在 `_sharedAncientSubset == null` 时直接 return，而该字段只对第二幕及之后有值
  （原版 `RunManager.GenerateRooms` 里 `State.Acts.Skip(1)` 才调 `SetSharedAncientSubset`）。
  第一幕的 `AllAncients`（`Overgrowth` / `Underdocks`）也是硬编码单元素列表。
- **接管位置**：`scripts/Patches/Act1AncientPoolPatch.cs`，Postfix 于 `ActModel.GenerateRooms`。
  以 `____sharedAncientSubset == null && Index == 0` 限定为第一幕，收集 `ShowAct == 1` 且
  `IsValidForAct` 通过的自定义先古之民，和原版抽中的涅奥合并后重新均匀抽取。
- **新增一层先古之民**：只要在 `TouhouAncientBase` 子类里写 `ShowAct => 1` 即可被自动纳入，
  无需再改补丁。
- **不需要跨幕去重**：一层候选（`ShowAct == 1` 的自定义先古之民 + 涅奥）不可能在二/三幕出现——
  `IsValidForAct` 判定 `act.ActNumber() == ShowAct`，ShowAct 为 1 时在二/三幕恒为 false，
  BaseLib 的 Prefix 会把它们剔除；涅奥也只硬编码在第一幕的 `AllAncients` 里。
  且原版按幕索引 0→1→2 生成，第一幕抽签时其他幕尚无 Ancient。
  BaseLib 的去重是为了拦住 `ShowAct` 为 `null`（二/三层通用）的先古之民在二三幕重复，
  那类候选不进本补丁。
- **随机流**：用 `new Rng(CurrentGeneratingRunState.State.Rng.Seed, act.Id.Entry)` 派生 RNG，
  不消耗原版 `State.Rng.UpFront`，避免打乱后续幕与地图的随机序列；各端结果一致。
- **涅奥专属表现**：`TouhouAncientBase.BeforeEventStarted` 中当 `ShowAct == 1` 时复刻涅奥两步
  （非读档时先 `SetCurrentHpInternal(0m)` 再靠 base 回满，随后 `NRun.Instance.GlobalUi.TopBar.Hp.LerpAtNeow()`）。
  用 override 而非 Transpiler，因为 `BeforeEventStarted` 是 async，逻辑在状态机 `MoveNext` 里。
- **哆来咪的第 4 个选项「离开梦境」**：实现在 `scripts/ancients/LeaveDream/`（逐玩家把事件实例换成涅奥 +
  台词与场景溶解演出），追加入口是 `TouhouAncientBase.ExtraOptions`，补丁在 `scripts/Patches/LeaveDreamPatches.cs`。
  机制、存档语义与注意事项见 **7.15**。
- **带 Modifier 的局（每日 / 自定义挑战）**：涅奥是第一幕第一间房里唯一发放 Modifier 奖励的地方，而一层
  先古之民与涅奥同池、会顶替它，所以这种局里 `TouhouAncientBase.GenerateInitialOptions` 整页照搬涅奥那套 ——
  只有 Modifier 选项，没有本 Mod 的遗物选项与「离开梦境」；没有 Modifier 的局保持原样。
  例外：本局的 Modifier **一个都不提供涅奥选项**时不照搬（原版那条路是空表 → 整页只剩「继续」），
  改为回落到正常选项，这是给 Zone the Spire 这类"隐形 Modifier"留的兼容口子。见 **7.17**。
- **设置页提示（两个一层先古之民都被禁用）**：两个都禁用又没有别的一层先古之民时，第一幕会被 `BanAncientPatch`
  的 Transpiler 过滤成空池。`TouhouAncientsConfig.SetupConfigUI` 覆写 BaseLib `SimpleModConfig`：`base` 跑完后按
  节点名 `CollapsibleSection_<ConfigSection 字符串>` 取该分区的 `NConfigCollapsibleSection.ContentContainer`
  （`BaseLib.Config.UI`），把一行警告追加到两个开关下方；显隐随 `ConfigChanged`（开关会调 `ModConfig.Changed()`）
  与 `OnConfigReloaded` 刷新。回调要登记进 `SimpleModConfig._configChangedHandlers` / `_configReloadedHandlers`，
  由 `ClearUIEventHandlers()` 注销（设置页关闭后节点已被 `QueueFreeSafely` 释放，自己 `-=` 会漏）。整段包 try/catch：
  BaseLib 的 `SetupConfigUI` 一旦抛异常，会把整个 Mod 设置页替换成错误提示。

**随机附魔**（附魔「梦色」、遗物「无穷无尽的愤怒」）：

- 池：`ModelDb.AllAbstractModelSubtypes` 里所有 `EnchantmentModel` 非抽象子类 → `ModelDb.GetId(type)` + `ModelDb.GetByIdOrNull<EnchantmentModel>(id)`（取不到就 `continue`）。
- 抽之前必须 `OrderBy(e => e.Id.ToString(), StringComparer.Ordinal)`：子类枚举顺序依赖程序集加载顺序，各端不同，而 `UnstableShuffle` 结果依赖初始顺序，不排序会导致联机各端随到不同附魔。
- 抽取：`candidates.UnstableShuffle(player.RunState.Rng.CombatCardGeneration).First()`，再 `CardCmd.Enchant(randomEnchantment.ToMutable(), card, amount)`。
- 排除：`DeprecatedEnchantment`（已删除附魔的空壳）、`IsMock`（`MockFreeEnchantment` 临时免费附魔等测试用附魔）、`Goopy`、`Bloodshed`、`Yumeiro`、`CanBeRandomSelected == false` 的 `TouhouAncientEnchantmentModel`（`BloodPond` / `Greed` / `Trick`）。
- 层数：统一走 `TouhouAncientEnchantmentModel.GetRandomEnchantAmount(e)`——`Sown`（播种）1、`Swift`（迅速）2、`Vigorous`（活力）6，其余看 `EnchantmentModel.ShowAmount`：true（原版锋利、灵巧、伶俐、动量、迅速、活力；本 Mod 蛊毒、付丧之力）取 3，false（原版播种、墨影、腐化、注能、黏糊等；本 Mod 奇迹、喋血、优质等）取 1。`Amount` 是基类属性、人人都有，不能用反射判断「有没有 Amount」，`ShowAmount` 才是唯一现成钩子（已核对：所有版本 `BaseLib.dll` 元数据里都没有 `ShowAmount`，即 `CustomEnchantmentModel` 没有覆写它，只有 `MedicinePoison` 蛊毒与 `Tsukumogami` 付丧之力覆写为 true）。新增随机附魔来源时不要再硬编码层数。

需要「某场战斗内的实时数据」时（如 `MiracleAgain`）——核心存档里没有任何出牌记录，只能自己追踪：新建 `BadgeModel` 子类（`ShouldReceiveCombatHooks => true`；`ModelDb.Init` 会实例化 `AllAbstractModelSubtypes`（含 mod 类型），`ModelDb.BadgeModels` 自动收录，**无需 `[Pool]`、无需注册、无需自己写 Harmony**），在 `BeforeCombatStart()` 清零、`AfterCardPlayed(choiceContext, cardPlay)` 里用 `LocalContext.IsMine(cardPlay.Card)` 过滤本玩家后计数。局内标志存 `SpireField<Player, bool>`，在 `Entry.Init` 里用 `ExtendedSaveHandlers<Player, SerializablePlayer>.RegisterSave<bool>(id, getter, setter, (v,w)=>w.WriteBool(v), r=>r.ReadBool())` 写进 `SerializablePlayer` 的扩展存档（存档多出 `save_dict_*` 键）；徽章侧用 `ExtendedSaveHandlers<Player, SerializablePlayer>.ExtendedData[player].DictForType<bool>().GetValueOrDefault(id)` 读。**坑**：deserializer 只收 `PacketReader` 一个参数；值类型时泛型的 `T?` 不生效（`value ?? false` 报 CS0019）；`RegisterSave` 必须早于序列化上下文初始化（即放 `Entry.Init`）。

标志统一走 `BadgeFlags`（`SpireField<Player, HashSet<string>>` + 每个 id 注册一次 `RegisterSave<bool>`）：徽章暴露 `FlagId` / `Unlock(player)` / `RegisterSave()`，`Entry.Init` 逐个调用。**需要卡牌自身效果期间的实时统计时，直接写在那一张卡的 `OnPlay` 里**（如 `AllCreationHisou` 打出循环里 `++hitNum`，到 24 就 `AllHumansFlyToTheSky.Unlock(player)`）；不要用 `BadgeModel` + `BeforeCardPlayed` / `AfterCardPlayed` 开窗绕 —— `AfterCardPlayed` 触发时卡牌内嵌套的 autoplay 早已跑完，窗口边界也无从定义。**要读的信号是别的模型的私有状态时**（如 `DuplexBarrier._wasSkippedThisRoom`）直接 postfix 那个模型自己的 Hook，用 `Traverse` 读私有字段，不要在别处复刻判定逻辑。纯牌组可算的（如 `ServantFamilyPhoto`）直接用 `IsObtained` 里的 `HasCard<T>` / `HasRelic<T>` + `player.CharacterId`，不需要追踪器。

#### 有值 / 无值的双分支文本（`cond:`）

`StringVar` 的默认值是空串 `""`（`StringVar(string name, string baseValue = "")`，且 `ToString()` 返回 `StringValue`），
所以「运行时才知道具体是什么」的文本可以用 SmartFormat 的 `cond:` 做双分支：未赋值时（事件界面预览）显示泛化文本，
赋值后（拾起时）显示具体名称。原版 `ArchaicTooth`（古老牙齿）与 `TouchOfOrobas`（欧洛巴斯之触）用的就是这个写法。

```text
{变量名.StringValue:cond:非空时显示的文本|为空时显示的文本}
```

#### 遗物选项的动态文本：必须在选项生成阶段就填好

如果某个 Ancient 遗物的描述里含有依赖当前对局的内容（例如「替换掉你的初始遗物」这种需要写出具体遗物名的文本），
该内容**必须在事件选项生成阶段确定**，不能等到 `AfterObtained`。

原因：事件界面在玩家拾起之前就会渲染遗物描述。`AfterObtained` 是在 `RelicCmd.Obtain` →
`player.AddRelicInternal` 之后才调用的，那时文本早已渲染过一遍，`StringVar.StringValue` 还是空串，
描述里只会一直显示 `cond:` 的兜底分支。

BaseLib 为此提供了与 `SetupForPlayer` 等价的钩子 —— `CustomAncientModel.AncientOption<T>` 的 `relicPrep` 参数
（对应 `AncientOption<T>.ModelPrep`，由 `ModelForOption` 在 `GenerateInitialOptions()` 时调用）：

```csharp
protected override OptionPools MakeOptionPools => new OptionPools(
    MakePool(AncientOption<IridescentDream>(relicPrep: PrepIridescentDream), /* ... */));

private RelicModel PrepIridescentDream(IridescentDream relic)
{
    if (Owner != null) relic.SetupForPlayer(Owner);
    return relic;
}
```

配套写法（参照原版 `TouchOfOrobas` / `ArchaicTooth`）：

- 把目标存进 `[SavedProperty]`（`ModelId?` 或 `SerializableCard?`），这样读档时 setter 会重新执行；
- 在**属性 setter** 里重建 `StringVar.StringValue` 与 `_extraHoverTips` —— 克隆与读档都能自动恢复；
- `AfterCloned()` 里重置 `_extraHoverTips` 后，靠 `SetupForPlayer` 再次赋值触发 setter 重建；
- 该方法**不要**用遗物自身的 `Owner`（此阶段尚未设置），必须由调用方传入玩家，
  在 ancient 里就是 `Owner`（即 `AncientEventModel.Owner`，可能为 null，需判空）。

只需要按「当前对局状态」算值、不需要存档的目标可以简化：不必 `[SavedProperty]`、不必在 setter 里重建，
`CanonicalVars` 里放一个空 `StringVar`，`SetupForPlayer` 直接算完写进 `StringValue` 即可。
例：遗物「无穷无尽的愤怒」（`Wuqiongwujindefennu`）按 `player.RunState.Players.Count > 1` 决定事件描述里
写「群情激愤」还是「愤怒」——牌名取自 `ModelDb.Card<Outrage>()` / `ModelDb.Card<Anger>()` 的 `Title`（跟着当前语言走，
不要在代码里硬编码中文），文本侧用
`{AngryCard.StringValue:cond:[gold]{AngryCard}[/gold]|[gold]群情激愤[/gold]（多人）/[gold]愤怒[/gold]（单人）}`，
未填值时（图鉴、控制台枚举选项）自动落到兜底分支；`description`（图鉴）保持静态双分支文本，`eventDescription` 用变量。

## 4. 内容类型开发规范

### 4.1 遗物

```csharp
[Pool(typeof(SharedRelicPool))]
public class Xxx : TouhouAncientRelics
{
    // 拾起：HasUponPickupEffect + AfterObtained
    // 战斗 Hook：直接重写虚方法
    // 多人：每个 Hook 检查 player != base.Owner（或等价 Owner 判断）
}
```

图标由基类按类名小写解析。休息处触发参考原版 `EternalFeather`：`AfterRoomEntered` + `room is RestSiteRoom`。

**先古选项条件**：覆写 `CanAppear(Player?)`（`TouhouAncientRelics` 的虚方法），返回 false 时 `TouhouAncientBase` 在抽取前就把它剔除，选项里不会出现。参考 `Jinsiliangjideyingzhang`（缺少的非先古休息处遗物少于 2 件时返回 false）、`GrilledMiso`（牌组里没有可升级的牌时返回 false）。判定「玩家是否已拥有」用 `player.Relics.All(owned => owned.Id != relic.Id)`（`ModelId` 比较，不要比实例）。

原版休息处遗物类名（`MegaCrit.Sts2.Core.Models.Relics`）：`Girya`（壶铃）、`RegalPillow`（皇家枕头）、`Shovel`（铲子）、`TinyMailbox`（小邮箱）、`DreamCatcher`（捕梦网）、`MiniatureTent`（微型帐篷，`RelicRarity.Shop`，效果是休息处可选任意数量选项）。

**判定遗物身份一律用 `Rarity`，不要列举具体遗物或用 ID 集合。** 三类分别对应 `RelicRarity.Starter` /
`RelicRarity.Ancient` / 其余（Common/Uncommon/Rare/Shop/Event）。

- **初始遗物**：`Character.StartingRelics` 是角色模型上的静态定义，`Player.PopulateStartingRelics()` 只在开局把它放进遗物列表；
  之后即使通过 `RelicCmd.Replace` 换成了升级版（如原版「欧洛巴斯之触」把 `BurningBlood` 换成 `BlackBlood`），
  `Character.StartingRelics` 也不会同步。而这 5 个升级版（`BlackBlood` / `RingOfTheDrake` / `DivineDestiny` /
  `PhylacteryUnbound` / `InfusedCore`）的 `Rarity` 依然都是 `Starter`，所以按 `Rarity` 判断能自动涵盖。
  参考实现：`IridescentDream`、`Yuuma/BottomlessStomach`。
- **先古遗物**：`Rarity == RelicRarity.Ancient` 与「先古事件选项」一一对应，不必再遍历
  `ModelDb.AllAncients.SelectMany(a => a.AllPossibleOptions)` 去收集 `EventOption.Relic` 的 ID。
  已核对：原版 100 个 `Ancient` 稀有度遗物的名字全部出现在 `Events/*.cs` 的事件代码里；本 Mod 的
  `TouhouAncientRelics` 子类（`Rarity` 恒为 `Ancient`）除 3 个弃用类（`HakureiCharm` / `LoseMoney` / `WhiteFlag`）
  外也全部在某个 Ancient 的 `TARelicOptionPools` 中出现。
  额外好处：本 Mod 先古遗物自身的 `Rarity` 也是 `Ancient`，在 `BottomlessStomach` 这类「吞噬除初始与先古外的所有遗物」
  的逻辑里可以自动排除自身，无需再写 `r != this`。

地图路线/节点标记（参照原版 `FurCoat`，参考实现 `Mamizou/DragonVeinVessel`）：

- `AfterObtained` 记录 `[SavedProperty] int ...ActIndex`（拾起时的幕），并用 `new Rng(Owner, Id)`（`MegaCrit.Sts2.Core.Random`）确定性随机，不污染主线随机
- `point.AddQuest(this)`（`MegaCrit.Sts2.Core.Map`）在节点上打标记，地图会显示小图标（`NMapPoint` 的 `Quests`）
- 坐标存入 `[SavedProperty] int[] ...CoordCols / ...CoordRows` + `bool ...CoordsSet`，读档/地图重生成时在 `ModifyGeneratedMapLate` 里 `map.GetPoint(coord).AddQuest(this)` 恢复
- 判定当前节点是否被标记：`RunState.CurrentMapPoint.coord` 与保存坐标比对（`MapCoord` 为 struct，可用 `==`/`Contains`）
- `MapPoint.Equals` 是 private（类外是引用比较），比较节点请用 `coord`

### 4.2 附魔

继承 `TouhouAncientEnchantmentModel`。可重写 `CanEnchantCardType`、`CanEnchant`、`OnEnchant`、`OnPlay`。

仅 Attack：`CanEnchantCardType(CardType cardType) => cardType == CardType.Attack`。  
排除 X 费：`card.EnergyCost.CostsX` / `card.HasStarCostX`。  
进入弃牌堆：`card.Pile?.Type == PileType.Discard`，并用 `oldPileType != PileType.Play` 排除正常打出。

从 `ModelDb` 牌池（`GetUnlockedCards` 等）筛候选时，返回的是 **canonical 模板**，不要调 `CanEnchant`。`CardModel.Owner` 会 `AssertMutable()`；其他模组给 `CanEnchant` 打的 Harmony 补丁也可能读 `Owner`，从而 `CanonicalModelException`。池子过滤只用模板上安全的字段（`CanEnchantCardType`、`CanonicalStarCost`、`HasStarCostX`、`Tags`、`CanBeGeneratedInCombat` 等）。`CardFactory.GetDistinctForCombat` 生成带 Owner 的战斗实例后，再对那张可变卡调 `CanEnchant`。

附魔会进战斗 Hook 监听器，可重写 `AfterDamageGiven`、`BeforeDamageReceived` 等全局 Hook。独有 Hook：`OnPlay`、`AfterCardPlayed`、`BeforeFlush`、`AfterCardChangedPiles`、`BeforeCardRemoved`。

无 `[SavedProperty]` 的附魔不必在 `Entry.cs` 注册。

一次性效果用 `base.Status = EnchantmentStatus.Disabled`（需 `MegaCrit.Sts2.Core.Entities.Enchantments`），不要自己做 `_hasTriggered`。

多人同步：**反射枚举（如 `ModelDb.AllAbstractModelSubtypes`）的顺序依赖程序集/类型加载顺序，联机各端不保证一致**。若用它构造候选列表再做 `UnstableShuffle(rng)`（结果依赖列表初始顺序），即使 Rng 流同步，各端也会随机到不同结果。必须在构建缓存时按 `ModelId` 确定性排序：`list.OrderBy(e => e.Id.ToString(), StringComparer.Ordinal).ToList()`（原版 `ModelDb` 亦用 `orderby ... Id.Entry`）。参考 `Yumeiro.cs` 的 `AllEnchantments`。

### 4.3 卡牌

- 继承 `TouhouAncientCards`（`abstract`）
- **具体类必须有 `public` 无参构造函数**，链到 `base(energyCost, type, rarity, targetType, shouldShowInCardLibrary)`
- 基类无参构造器目前是注释掉的，不要依赖它
- 常量放类顶部 `private const`
- `[Pool(typeof(EventCardPool))]` 需要 `using BaseLib.Utils;` 与 `using MegaCrit.Sts2.Core.Models.CardPools;`
- 无需在 `Entry.cs` 注册
- `OnUpgrade` 里用 `base.DynamicVars["Key"].UpgradeValueBy(...)`，不要改 Canonical 默认值字段

```csharp
[Pool(typeof(EventCardPool))]
public class ExampleCard : TouhouAncientCards
{
    private const int energyCost = 1;
    private const CardType type = CardType.Skill;
    private const CardRarity rarity = CardRarity.Ancient;
    private const TargetType targetType = TargetType.Self;
    private const bool shouldShowInCardLibrary = true;

    protected override IEnumerable<DynamicVar> CanonicalVars =>
    [
        new DynamicVar("Damage", 8)
    ];

    public ExampleCard() : base(energyCost, type, rarity, targetType, shouldShowInCardLibrary) { }

    protected override async Task OnPlay(PlayerChoiceContext choiceContext, CardPlay cardPlay) { }

    protected override void OnUpgrade()
    {
        base.DynamicVars["Damage"].UpgradeValueBy(3m);
    }
}
```

| Hook / 成员 | 说明 |
|-------------|------|
| `OnPlay` | 打出效果 |
| `OnUpgrade` | 升级改 DynamicVars |
| `GetResultPileType` | 弃牌去向；回手返回 `PileType.Hand` |
| `GetResultPileTypeForCardPlay` | Quest/能力打出后移出战斗用 `PileType.None` |
| `CanPlay` / `IsPlayable` | 打出限制。**新增**限制优先覆写 `IsPlayable`；破除诅咒/灼伤禁打才用 Harmony Patch `CanPlay` |
| `CanonicalKeywords` | 固有/保留/虚无等 |
| `ExtraHoverTips` | 额外悬停 |
| `BeforeFlush` | 手牌检测阶段改费用 |
| `AfterCardEnteredCombat` | 卡牌**已进入**战斗牌堆后触发（`CardPileCmd.Add` 里 `AddInternal` 之后、`oldPile == null && targetPile.IsCombatPile` 时）。适合做"生成后自动配对"逻辑（如封魔阵进弃牌堆自动找目标牌）。此时 `card.Pile` 已是目标牌堆 |
| `AfterTransformedFrom` | 本牌被「变化」时触发。`CardCmd.Transform` 对原牌的顺序是 `RemoveFromCurrentPile()`（静默，不触发 `AfterCardChangedPiles`）→ 加入新牌 → `AfterTransformedFrom()` → `RemoveFromState()`，原牌**不进任何牌堆**，想在自己被变化时做收尾只能用这个回调。参考 `SealCircle`（被变化时解除封印） |
| `AddExtraArgsToDescription` | 覆写描述动态变量：往里 `description.Add("Key", value)`，覆盖 CanonicalVars 的默认值。可实现"非战斗/战斗已配对/战斗未配对"三态描述（SmartFormat 条件只能二选一）。**文本必须从本地化表读取**（如 `new LocString("cards", Id.Entry + ".descriptionIdle")`），不要硬编码中文，否则无法多语言。参考 `SealCircle` |

费用：`EnergyCost.AddThisTurn(n)`；`SetThisTurn` / `SetThisCombat`。  
辉星：`SetStarCostThisCombat(0)` / `SetStarCostThisTurn(0)` / `SetStarCostUntilPlayed(0)`。  
重放：`card.BaseReplayCount++`；实际次数 `GetEnchantedReplayCount() + 1`。

目标：`None` / `Self` / `SingleEnemy` / `AllEnemies` / `AnyCreature` / `AnyEnemy`。  
类型：`Attack` / `Skill` / `Power` / `Curse` / `Quest`。  
稀有度常用 `CardRarity.Ancient` 或 `CardRarity.Quest`。

> **注意**：`AfterCardGeneratedForCombat` 是给**生成者**监听的 Hook（creator 是玩家；敌人施加状态牌时 creator 为 null，且文档明确排除敌人施加的状态牌），**不适合**在"敌人生成的状态牌自身"上做逻辑。要监听"牌自己被放进战斗牌堆"，用 `AfterCardEnteredCombat`。

### 4.6 `[SavedProperty]`

- 只能标在**自动属性**上，不能标字段
- 建议前缀 `TouhouAncients_`
- 有 `[SavedProperty]` 的类型才需要 `SavedPropertiesTypeCache.InjectTypeIntoCache(typeof(T))`
- 仅 `[Pool]`、无 SavedProperty 的类型不注册
- `Entry.cs` 里目前相关调用都被注释掉了；若读档丢状态，先检查是否漏注册
- **「次数/场次/计数器」这类跨房间累计状态必须走 `[SavedProperty]`**：普通字段读档后回到声明初值，
  用 `_initialized` 之类的惰性初始化还会把它重新灌成上限值，表现为「用不完」。
  参照原版 `WingedBoots.TimesUsed`、`KompeitoPot.TouhouAncients_UsesRemaining`：
  在 setter 里同步 `DynamicVars`、`InvokeDisplayAmountChanged()` 和 `Status`，读档时这些显示状态才会跟着恢复。

### 4.6.1 怪物演出（灵梦灵符参考）

帧动画怪物做"技能演出 + 场景子节点动画"的参考实现：

- **视觉辅助脚本**：新建继承 `NCreatureVisuals` 的类（如 `scripts/Vfx/HakureiReimuVisuals.cs`）挂在 `creature_visuals/{怪物}.tscn` 根节点，`[Export]` 场景子节点引用（如 `AmuletRoot`），在 `_Ready` 中 `base._Ready()` 后缓存子节点（`GetNodeOrNull<AnimatedSprite2D>`）。怪物侧用 `base.Creature.GetCreatureNode()?.Visuals as HakureiReimuVisuals` 获取。
- **运行时建逐帧动画**：`new SpriteFrames()` + `AtlasTexture { Atlas, Region }` + `AddFrame("default", atlas)`，`SetAnimationSpeed` / `SetAnimationLoop` 控制播放；`AnimatedSprite2D` 没有 `Loop` 属性，必须用 `SpriteFrames.SetAnimationLoop`。
- **切换动画保持当前帧**：`AnimatedSprite2D.Animation` 切换会重置帧，先记录 `amulet.Frame`，切完 `Mathf.Min(当前帧, 新动画帧数-1)` 恢复。
- **位移演出**：`CreateBodyMoveTween(body)`（基类提供，死后自动锁回原位）+ `TweenProperty(body, "position", ...)`；子节点（灵符）直接 `CreateTween().TweenProperty(amulet, "global_position", ...)`，用 `AwaitFinished`（`MegaCrit.Sts2.Core.Nodes.GodotExtensions`）等待完成。
- **禁止受击动画**：重写 `ShouldPlayHurtAnimation => !_isAnimating`，演出开始时置位、结束后复位。
- **坐标系**：`creature_visuals` 根（NCreatureVisuals）与 `NCreature` 原点一致（`Visuals.Position = Vector2.Zero`），场景内 Marker2D（CenterPos/灵符目标）的 `GlobalPosition` 与 `creatureNode.VfxSpawnPosition` 同坐标系，可直接互算。
- **意图位置**：战斗里真正画意图的是 `NCreature.IntentContainer`（`%Intents`），和 `Visuals` 是兄弟节点。原版只在私有 `UpdateBounds` 里执行 `IntentContainer.Position = IntentPos.Position - IntentContainer.Size / 2f`（用 Marker 的本地 `Position`，不乘 `Visuals.Scale`）。`ScaleTo` 不会调用 `UpdateBounds`。改 `IntentPosition.GlobalPosition` 不会让图标跟着动；缩放后要意图跟着走，直接写 `IntentContainer.Position`。身体节点用 `NCreature.Body` / `Visuals.GetCurrentBody()`，`NCreatureVisuals` 没有 `Body`。参考 `BloodDisasterPower.ChangeAmount`。
- **坑**：在继承 `NCreatureVisuals` 的脚本类里 `AddChildSafely`/`QueueFreeSafely`（`MegaCrit.Sts2.Core.Helpers.GodotTreeExtensions`）可能报 CS0103（Godot 源生成器上下文问题），改用 `AddChild`/`QueueFree` 原始 API。

### 4.6.2 怪物演出（辉夜五道难题漂浮谜题参考）

怪物周围"漂浮环绕物品 + 按进度淡出"的参考实现（`scripts/Vfx/HouraisanKaguyaVisuals.cs` + `scenes/creature_visuals/HouraisanKaguyaMonster.tscn`）：

- **环绕旋转动画**：tscn 内联 `sub_resource type="Animation"`（`loop_mode=1` 循环，`resource_name` 与键一致）+ `AnimationLibrary`（含 `RESET` 空动画与主动画）+ 节点段挂 `AnimationPlayer`（`libraries = {&"": SubResource(...)}`）。动画不设 `autoplay`，由脚本在技能释放时 `PuzzleAnimPlayer.Play("puzzle_orbit")` 启动。
- **远近变化**：绕椭圆轨道做 `position` 关键帧（8 采样/圈，`tracks/N/type="value"`，`values` 为 `Vector2` 数组），每个物品各一条 `scale` 轨道与椭圆纵向位置联动（近处大、远处小），相位错开（如 5 个物品各偏移 72°）形成环绕流动感。`update: 0` 表示插值更新。
- **按进度淡出**：`Power → Monster → Visuals` 回调链（同 4.6.1）：Power 的 `CompletePuzzle` 内 `base.Owner.Monster is XxxMonster` 后调怪物方法 → 怪物查 Power 完成数（Power 暴露 `GetCompletedPlayerCount`）→ Visuals `UpdatePuzzleTransparency(puzzleType, completedCount, playerCount)`。多人按比例 `alpha = 1 - completedCount / playerCount`，全部完成时淡出后 `visible=false`。
- **淡入淡出**：`Sprite2D` 用 `modulate:a` 渐变（`CreateTween().TweenProperty(puzzle, "modulate:a", ...)`）。注意 `TweenCallback` 是 `Tween` 的方法，不能接在 `TweenProperty`（返回 `PropertyTweener`）后面链式调用，需先取 Tween 变量再分别调用。
- **开场隐藏**：根节点（PuzzleRoot）默认 `visible=false`，释放技能时才显示；`z_index` 高于怪物本体避免被遮挡。
- **节点悬停 HoverTip（多人显示未完成玩家）**：`NHoverTipSet.CreateAndShow(Control owner, hoverTips, alignment)` / `NHoverTipSet.Remove(owner)` 是全局 HoverTip 系统（`MegaCrit.Sts2.Core.Nodes.HoverTips`）。在每个谜题 Sprite2D 下挂子 `Control`（`mouse_filter=0` Stop，offset 定义命中矩形，随父 Sprite 变换缩放/旋转），Visuals 在 `_Ready` 连接 `MouseEntered/MouseExited`。进入时从怪物（`GetParent<NCreature>()?.Entity.Monster as XxxMonster`）查未完成玩家名（Power 暴露 `GetIncompletePlayerNames`），用 `LocString.Add("PlayerNames", ...)` 注入 SmartFormat 变量后 `CreateAndShow(hitbox, new HoverTip(desc), HoverTip.GetHoverTipAlignment(hitbox))?.SetFollowOwner()`；移出时 `Remove(hitbox)`。**坑**：`SetFollowOwner` 依赖 owner 与 HoverTip 的相对偏移（`CreateAndShow` 时 `SetAlignment` 先定位），不能配 `HoverTipAlignment.None`，否则 HoverTip 固定到原点。图标隐藏（visible=false）后子 Hitbox 随之失效，自然不可悬停。
- **坑**：新建 `.cs` 脚本的 `.uid` 文件需手动创建（格式 `uid://xxx` 单行）并填到 tscn 的 `[ext_resource type="Script" uid="..." path="..."]`，否则 Godot 打开场景会重新生成 uid 导致引用失配。

#### 在 `AfterActEntered` 里 `OfferCustom` 必须先把地图界面关掉

**症状**：在 `AfterActEntered()` 里调 `RewardsCmd.OfferCustom`，奖励面板「弹不出来」或一弹出来就被整块黑幕盖住、点不动。

**成因**（三件事叠加）：
1. `RunManager.EnterAct`（`RunManager.cs`）的顺序是 `EnterRoomInternal(new MapRoom())` → `ActEntered` 事件 → `FadeIn` → `Hook.AfterActEntered`。所以钩子执行时**新幕的地图房间已经进入**，`NMapRoom._Ready` 里已经调用 `NMapScreen.Instance.Open()` + `SetTravelEnabled(true)`。
2. `scenes/run.tscn` 中 `GlobalUi` 的子节点顺序是 `OverlayScreensContainer`(含 `OverlayBackstop`) → **`MapScreen`** → `CapstoneScreenContainer`。Godot 按兄弟顺序绘制，因此地图画在所有 overlay **之上**；`MapScreen` 根节点 `mouse_filter` 默认 `Stop`，鼠标事件也被它吃掉。
3. `NOverlayStack._Ready` 的显示机制是「地图 `Opened` → `HideOverlays` / 地图 `Closed` → `ShowOverlays`」。地图先开、奖励面板后推，`Opened` 信号不会再触发，面板永远等不到 `ShowOverlays`。

另外 `ActiveScreenContext.GetCurrentScreen()` 里 `NMapScreen.IsOpen` 的判定排在 `NOverlayStack.Peek()` 之前，所以按键/焦点也归地图，手柄同样无法操作奖励面板。

#### 只关掉地图还不够：ESC 会把它重新打开

`NMapRoom._Ready` 把 `NCapstoneContainer.CapstoneClosed` 连到了自己的 `ReopenMap()`。玩家在奖励面板上按 **ESC 打开暂停菜单、再关闭暂停菜单**时会发出 `CapstoneClosed` → 地图 `Open()`。
因为 `Close()` 已经把 `IsOpen` 置为 `false`，`ReopenMap` 里的 `Open()` 不会早退，它会：

1. 发出 `Opened` 信号 → `NOverlayStack.HideOverlays` 把奖励面板淡出；
2. 作为 `OverlayScreensContainer` 的后一个兄弟节点重新画在 overlay 之上（地图 `_backstop` 又变回不透明）；
3. 保留 `NMapRoom._Ready` 设的 `SetTravelEnabled(true)`——玩家一点节点就 `ExitCurrentRoom`，未领取的奖励会被 `RewardsSetSynchronizer.BeforeLeavingRoom()` 直接跳过。

这就是「按 ESC 再关闭，奖励界面就被吞了」的成因。

**正确写法**（参照 `SupremeDream`）：关掉地图后**连上 `NMapScreen.Opened` 信号**，一旦地图被重新打开就立刻再关一次；`Close` 会发出 `Closed` 信号，`NOverlayStack` 收到后调 `ShowOverlays` 把面板重新显示出来。再用 `try/finally` 保证异常时也恢复地图。

```csharp
var mapScreen = NMapScreen.Instance;
bool ownsMapScreen = LocalContext.IsMe(player) && (mapScreen?.IsOpen ?? false);

Callable mapReopenedGuard = Callable.From(CloseMapScreenWhileRewardsAreShown);
if (ownsMapScreen)
{
    mapScreen!.Close(animateOut: false);
    mapScreen.Connect(NMapScreen.SignalName.Opened, mapReopenedGuard);
}

try
{
    // …构建 rewards…
    await RewardsCmd.OfferCustom(base.Owner, rewards);
}
finally
{
    // 地图是本幕唯一能继续往下走的入口，漏掉这一步会把玩家永久卡在地图房里。
    if (ownsMapScreen && mapScreen != null && GodotObject.IsInstanceValid(mapScreen))
    {
        mapScreen.Disconnect(NMapScreen.SignalName.Opened, mapReopenedGuard);
        mapScreen.Open();
    }
}

// 回调本体必须是实例方法，不能用 lambda——lambda 每次求值都会产生不同的 Callable 实例，导致 Disconnect 失配。
private static void CloseMapScreenWhileRewardsAreShown() => NMapScreen.Instance?.Close(animateOut: false);
```

连接顺序对我们有利：`NOverlayStack` 的 `HideOverlays` 在很早（`NOverlayStack._Ready`，早于本遗物的 `AfterActEntered`）就接上了，所以同一次 `EmitSignalOpened` 里会先被隐藏、再由 `Close()` 触发 `ShowOverlays` 重新显示，面板不会真的消失。
残留副作用：`NMapScreen.Open` 内部的 `SfxCmd.Play("event:/sfx/ui/map/map_open")` 在我们关闭之前已经播放，所以按 ESC 再关闭暂停菜单时能听到一声地图打开的提示音（视觉上地图不会真正显示出一帧）。

其余要点：
- 用 `LocalContext.IsMe(player)` 收口：只有本机玩家才需要这个补救（只有他会看到自己的面板），多人下也就不会在等远端选择期间反复开关地图。
- `OfferCustom` 产出的面板 `isTerminal == false`（只有战斗/宝箱房奖励才是终局），最后一个奖励被取走或跳过后它会自行调 `NOverlayStack.Remove`，所以 `await` 返回时 overlay 栈已空，紧接着 `Open()` 地图正好回到「选择下一个房间」流程。
- 第二幕及之后 `ActFloor != 0`，`Open()` 不会重播开场动画、也不会重复生成幕横幅（该逻辑限定 `ActFloor == 0` 且 `!_hasPlayedAnimation`）。
- 回调必须写成实例方法（或存字段），不能每次现写 lambda；`finally` 里的 `Disconnect` 要配上同一个 `Callable` 实例。
- 次要影响：`Hook.AfterActEntered` 在 `RunManager.EnterAct` 的 `using (new NetLoadingHandle(NetService))` 作用域内被 await，所以 `await OfferCustom` 会把整个「进幕」流程挂到玩家选完奖励为止（多人下 loading 标记一直为真、远端的超时遮罩被抑制，其他 `AfterActEntered` 监听器如 `CursedRun` 也被延后）。需要避免的话就别在 `AfterActEntered` 里发面板，改为在下一幕第一个房间的 `AfterRoomEntered` 里 fire-and-forget。

### 5.9 Harmony 补丁要点

`harmony.PatchAll()` **只处理类上带 `[HarmonyPatch]` 的类型**。方法上还要有 `[HarmonyPostfix]` / `[HarmonyPrefix]` 等；光写 `[HarmonyPatch(...)]` 且方法名带 Postfix **不会**自动当 Postfix。参考 `NamelessYoukaiGlowPatch`。

指定卡牌可打出（破除 Unplayable）：Patch `CardModel.CanPlay`。`CurseBreakerQi` 对诅咒；`HinezumiNoKawagoromo` 对 `Burn`。

手牌红蓝流光：Postfix `CardModel.ShouldGlowGold` getter，再 Postfix `NHandCardHolder.UpdateCard` 换材质。shader：`res://shaders/nameless_youkai_flow.gdshader`。必须同步 `NCardHighlight` 私有字段 `_shaderMaterial`。

获得能量后钩子：Patch `PlayerCmd.GainEnergy(decimal, Player)`。Prefix `Priority.First` 把当前能量写入 `__state`；Postfix `HarmonyPriority(-1)` 把返回 `Task` 包一层，等原方法跑完（能量已加上）后由 `AfterEnergyGainedIfChanged` 构造 `PlayerEnergyGainContext`，再传给 `PlayerEnergyGainHook.AfterEnergyGained(context)` 分发。`amount <= 0` 不分发。回合开始 `ResetEnergy` / `AddMaxEnergyToCurrent` 不走 `GainEnergy`，仍用 `AfterEnergyReset`。叠装 RitsuLib 时两套钩子各自包装 Task、各自听众；本补丁 Postfix 优先级比 RitsuLib 的 `Priority.Last == 0` 更靠后，顺序不跟 Mod 列表走。不要让同一模型同时实现本接口和 RitsuLib `IPlayerResourceHookListener`。参考 `PlayerEnergyGainHookPatch`、`WindPriestessWine`。

### 5.10 未名妖魔：手牌变化

`CardSelectCmd.FromHand`（MinSelect=0）。替换牌：`ModelDb.AllCharacterCardPools` 里同稀有度，`card.CardScope.CreateCard`，`CardCmd.Transform`。原卡已升级则 `CardCmd.Upgrade(replacement)`。

### 5.11 弃牌堆捞牌（SilenceDoll）

`AfterCardChangedPiles` 追踪进弃牌的牌；`AfterSideTurnStart` 用 `CardSelectCmd.FromSimpleGrid` 捞回手并 `AddKeyword(Retain)`；打出后若原本没有保留则 `RemoveKeyword`。战斗期数据，开战/结束清空，无需 SavedProperty。

### 5.12 回合奇偶

`combatState.RoundNumber % 2`。参考 `StageDevice`。

### 5.13 死亡预防

`ShouldDieLate` 返回 `false` 阻止死亡，再 `AfterPreventingDeath` 里治疗/扣最大生命。参考 `SoulButterfly`、`KonshiiNoKusuri`。

怪物死后只留尸体：不要把死掉的 `Creature` 留在敌人列表里（`PrepareForNextTurn`/`TakeTurn` 仍会跑）。可让 `ShouldCreatureBeRemovedFromCombatAfterDeath` 暂时 `false`，在自己的 `AfterDeath` 末尾 `CombatManager.RemoveCreature` + `combatState.RemoveCreature(creature, unattach: false)`，不要调用 `NCombatRoom.RemoveCreatureNode()` 直到要播 `NMonsterDeathVfx`。参考依神姐妹怪物。出招中途死亡时用 `unattach: true`，让原版 `PerformMove` 收尾的 `RemoveCreature` 因 `CombatState == null` 直接返回，避免二次移除。

帧动画怪物没有 Spine `attack_target_bone`，冲锋只能挪 `GetCurrentBody()`。`TouhouAncientMonsterBase.BeforeDeath` 会停位移 Tween、把身体拉回原位并播 `die`；死后 `PlayAnimation` / hurt 只允许 `die`。死后仍需播其它动画的怪物重写 `ShouldKeepAnimatingWhileDead`（紫苑双生）。位移用 `CreateBodyMoveTween` / `SetBodyPosition`。

### 5.13.1 回合接管（自动打牌）

参考 `WhisperingEarring`：在 `AfterAutoPrePlayPhaseEntered`（或 `Late` 版本）中自动打牌。要点：

- 打牌前先 `await card.SpendResources()`，再 `CardCmd.AutoPlay(choiceContext, card, target, AutoPlayType.Default, skipXCapture: true)`（`AutoPlay` 本身不扣能量，必须自己先花）。
- `CanPlay()` 会检查能量是否足够；每打一张重新扫描手牌（能量/手牌会变化）。
- 目标选择：`TargetType.AnyEnemy` 取 `combatState.HittableEnemies.FirstOrDefault()`；`AnyAlly` 取 `rng.NextItem(combatState.Allies.Where(...))`（空集合返回 null）；`AnyPlayer` 取自身。
- 按费用排序用 `card.EnergyCost.GetWithModifiers(CostModifiers.All)`，同费用保持手牌从左到右：`hand.Cards.Select((c,i)=>(c,i)).OrderByDescending(...).ThenBy(t=>t.index)`。
- 若 Power 要求"下回合才开始接管"：判断 `AmountOnTurnStart == 0`（`BeforeTurnStart` 每回合开头会把 `AmountOnTurnStart` 刷新为当前 `Amount`；当回合中途才添加的 Power 该值为 0）。
- 参考 `PossessedBySeigaPower`（走火入魔，霍青娥接管）、`WhisperingEarring`。

### 5.14 能量时序

```
AfterEnergyReset  ← 在这里加能量不会被重置
  ↓ BeforeHandDraw → 摸牌 → AfterPlayerTurnStart → AfterSideTurnStart → BeforePlayPhaseStart
```

`PlayerCmd.GainEnergy` 真正加上能量之后：`IPlayerEnergyGainedListener.AfterPlayerEnergyGained`（本 Mod 钩子，见 5.9）。获得能量后抽牌用 `ThrowingPlayerChoiceContext`，留在当前 GameAction 里；不要再 `new HookPlayerChoiceContext`。

### 5.15 CardModel.Owner

反序列化时 Owner 为 null；`RunState.AddCard()` 才设置。canonical 实例上不要假设 Owner 非空。

### 5.16 取「面板显示」的数值（含附魔修正）

面板值存在 `DynamicVar.PreviewValue`，由 `DamageVar.UpdateCardPreview` 算出：先加附魔修正（`EnchantDamageAdditive` / `EnchantDamageMultiplicative`，锋利就是这里 +Amount），再按 `runGlobalHooks` 决定是否跑全局 `Hook.ModifyDamage`。
`CardModel.UpdateDynamicVarPreview` 只在「战斗中且牌在手牌/打出区」时 `runGlobalHooks = true`；其余情况（如在牌组里、Boss 后奖励结算）只算附魔修正。

```csharp
card.UpdateDynamicVarPreview(CardPreviewMode.None, null, card.DynamicVars);
int damage = (int)card.DynamicVars.Damage.PreviewValue;
```

`BaseValue` 才是改状态的计算值，`PreviewValue` / `EnchantedValue` 仅供显示。直接调 `Hook.ModifyDamage` 会额外跑遗物/能力等全局修正，战斗外会与面板不一致。参考 `ParadiseDream`。

## 6. 注意事项

### 6.1 多人

每个会改状态的 Hook 检查所有权（`player != base.Owner` 或 `card.Owner`）。参考 Nina 遗物 `Yishixingqile`、`Yiyandingzhen`。动画用 `LocalContext.IsMine(card)` / `LocalContext.IsMe(player)`。

已经在某个 GameAction 里（例如 `await PlayerCmd.GainEnergy` 的续体、`AfterEnergyReset`）抽牌时，用 `ThrowingPlayerChoiceContext`。不要再 `new HookPlayerChoiceContext(..., GameActionType.CombatPlayPhaseOnly)`：一旦抽牌链路触发 `SignalPlayerChoiceBegun`，会再挂一层 Hook 动作，只有 `Owner.NetId == LocalContext.NetId` 的端会 enqueue，其它端等 `ExecutionStartedTask`，联机不同步。参考 `WindPriestessWine`。

### 6.2 脚本扫描

`abstract` 类不会被 Godot 脚本扫描器实例化。具体卡牌/遗物必须可被 `Activator.CreateInstance` 构造。

### 6.3 本地化名称匹配（替代 CardTag）

关键词放 `relics.json`，`LocString.GetFormattedText().Split(',')`，再对 `card.TitleLocString` 做 `Contains`。

### 6.4 MerchantEntry

`list.UnstableShuffle(rng).Take(N)`。商店刷新相关：`SuspiciousToken` + `MerchantRefreshEntry` + `NMerchantRefreshSlot`。

## 7. 大型专题

### 7.1 Ancient 挑战战斗

基类 `TouhouAncientBase` 已内置挑战选项。子类重写：

```csharp
public override SomeEncounter? ChallengeEncounter => ModelDb.Encounter<SomeEncounter>();
```

要点：

- 选项追加在 `GenerateInitialOptions` / `AllPossibleOptions`；子类自定义选项应重写 `GetAncientOptions()`，不要绕开基类
- 若重写 `GenerateInitialOptions()`，必须 `base.GenerateInitialOptions()`，否则挑战胜利遗物奖励为空
- 进入战斗：`EnterCombatWithoutExitingEvent(encounter, rewards, shouldResumeAfterCombat: false)`，传入 **canonical** Encounter（v0.110.1+）
- 挑战是终点：不回事件页；`ShouldGiveRewards => true`；`TouhouAncientEncounter.TryModifyRewards` 只保留 `CombatRoom.ExtraRewards`
- Encounter 默认 `ShouldReceiveCombatHooks => false`，所以 `Entry.Init` 用 `ModHelper.SubscribeForRunStateHooks` 把当前 `TouhouAncientEncounter` 注册进 RunState Hook
- `shouldResumeAfterCombat: false` 使事件不完成，避免 `EventRoom.OnEventStateChanged` 自动存档把奖励弄丢
- 每个玩家事件实例只收集 **本玩家** `_generatedRelicOptions`，不要遍历全员合集再合并（会变成人数倍）
- 回血：`ChallengeRewardPatch` Patch `Hook.AfterCombatVictory`，且 `LocalContext.IsMe(player)`
- 读档恢复跳过重复全回血：`AncientChallengeRestorePatch` 在 `isRestoringRoomStackBase` 时 `MarkPreFinished()`
- **多人读档回奖励页**：挑战胜利后 `EndCombatInternal` 写入 `PreFinishedRoom = CombatRoom`（读档重建父事件 + pre-finished 战斗房并弹奖励页）。但 `EventRoom.OnEventStateChanged` 在事件"全员完成"时会 `SaveRun(this)` 把 `PreFinishedRoom` 覆盖成 EventRoom（先古事件），多人共享事件时序下存在误判窗口，导致奖励页退出重进回到先古页面。`AncientChallengeOnEventStateChangedPatch` 拦截 `EventRoom.OnEventStateChanged`：仅当 `TouhouAncientBase.ChallengeCombatEntered == true`（已进入挑战战斗）时跳过自动存档；该标志在 `StartChallenge` 置位、会话级不持久化，"无人投挑战按玩家拿遗物"分支不置位，正常事件照常存档 DONE 页
- `IsChallenge` 用置位-复位，避免污染 canonical
- 挑战按钮图标：`AncientDialoguePortraitPatch` 里 Patch `NEventOptionButton._Ready`；用 `RunHistoryIcon` 不要直接加载 path；宽图 `ResetIconSize`；识别靠 `TextKey.EndsWith(".fight")`，角色专属标题不要改 textKey
- 挑战选项标题：默认 `{AncientId}.fight.title`。角色彩蛋键为 `{AncientId}.fight.{token}.title`，当 `Character.Id.Entry` 包含该 token（忽略大小写）时启用，更长 token 优先。例如妹红 ID 含 `MOKOU` 时用 `fight.mokou.title`。之后只加本地化即可扩展，不必改代码。匹配逻辑在 `CharacterLocVariant`
- 挑战选项描述：`TOUHOUANCIENTS.fight.description`
- 遭遇失败文本：默认 `{EncounterId}.loss`。角色彩蛋键为 `{EncounterId}.loss.{token}`（同样用 `CharacterLocVariant`）。`GetLossMessageFor` 不是虚方法，由 `EncounterLossMessagePatch` Postfix。例如妹红打辉夜用 `HOURAISAN_KAGUYA_ENCOUNTER.loss.mokou`
- 挑战死亡会先被记成事件死亡（`Rooms.First()` 仍是 Ancient 事件）。`EncounterLossMessagePatch` 在 `CreateRunHistoryEntry` 后把 `KilledByEncounter` 改成该地图点最后一场 `TouhouAncientEncounter`，死亡引言才会走 `GetLossMessageFor`。`TouhouAncientEncounter.cs` 里旧的 `TouhouAncientEncounterDeathQuotePatch` 仍整段注释，已由本补丁替代

多人投票（`AncientMultiplayerVotePatch`）：

- 只对 `ChallengeEncounter != null` 的 `TouhouAncientBase` 生效
- 全员挑战 → 原版；无人挑战 → 各拿各的遗物；混合 → 挂起改票
- 哨兵 `optionIndex = 15`（只有 4 位，不能用 `uint.MaxValue`）
- `GenerateInitialOptions` 用 `new Rng(Owner!, Id)` 让各玩家遗物池不同
- `IsPerPlayerResolution` 时跳过随机选择动画
- 多人给挑战选项加 `TOUHOUANCIENTS-CHALLENGE_COOP` HoverTip；`Owner != null` 才附加

### 7.2 挑战 BGM

`EncounterModel.CustomBgm` **不能**传 `res://` mp3。用 `EncounterBgm` + `AutoModAudio("res://debug_audio")`。原版 FMOD 用 `FmodAudio.SetBusMute("bus:/master/music", true/false)` 静音（与音量独立，不要 `SetBusVolume(0)`，也不要快照/回写总线音量）。mp3 跟 `SettingsSave.VolumeBgm`（开播 `LinearToDb`，滑块经 BaseLib postfix `ModAudio.UpdateVolumes`），走 Godot Master 总线，不受 FMOD mute 影响。子类重写 `BgmFileName`。默认战斗开始就播；`AutoStartBgm => false` 时开场只 mute 原版，由 `EncounterBgm.Start(file, fadeInSeconds)` 手动开始（淡入走 BaseLib `AudioStreamPlayer.FadeIn`）。辉夜在「五道难题」释放后淡入 2 秒，曲名也等到此时才显示。曲名走 encounters 本地化 `{Id.Entry}.bgm`，UI 场景 `res://scenes/ui/bgm_name_display.tscn`。循环看 `.import` 的 `loop=true`。`FmodAudio` 已 Obsolete，用 `#pragma warning disable CS0618`。

### 7.3 多人开局配置同步

BaseLib `SimpleModConfig` 各端本地文件不同步。仿 RitsuLib `RunSavedData`：本机设置只作提交源，开局写成局内数据 `AncientRunSavedData`，随原版开局包的 **字节包尾** 带到客户端（不打 `LobbyBeginRunMessage` 这个 struct 的 Serialize/Deserialize）。`ForcedAncientSyncPatch`：

- 局内字段 `ForcedAncient_2_Run` / `ForcedAncient_3_Run` / `BannedMask_Run`，必须 `[ConfigIgnore]`
- Prefix `RunManager.SetUpNewSingleplayer`：单人 `CommitFromLocalConfig`（清上一局联机残留）
- Prefix `ENetHost.SendMessageToClient` / `ENetClient.SendMessageToHost`（以及 Steam 对应方法）：首字节为 `LobbyBeginRunMessage` 时在 `length` 后追加 26 字节 trailer（页脚 `1SAT`，从包尾往前搜，可与其它 Mod trailer 共存）。不要 patch `NetMessageBus.SerializeMessage<T>`（Harmony 对 struct 泛型 + out 会 `InvalidProgramException`）
- Postfix `NetMessageBus.TryDeserializeMessage`：客户端 Apply 主机数据；本地设置文件不改
- Prefix `RunManager.GenerateRooms`：尚未提交则用本机设置（单人兜底；客户端已 Apply 则跳过）
- 禁用位序必须与 `GetBanBit` / `BuildBannedMask` 一致：0=Nonupeipe, 1=Vakuu, 2=Tanx, 3=Orobas, 4=Pael, 5=Tezcatara, 6=Darv, 7=Reimu, 8=Sanae, 9=Marisa, 10=Satori, 11=Tewi, 12=Seija, 13=Medicine, 14=Nina, 15=Remilia, 16=Tenshi, 17=Yuyuko, 18=Kaguya, 19=Junko, 20=Yuuma, 21=Yorigami, 22=Mamizou（类已注释，位已预留）

### 7.4 卡牌施加回合内 Power（独白 / 未名妖魔）

`PowerCmd.Apply<T>` 后给 Power 的 DynamicVars 赋值。`BeforeCardPlayed` 记录当前牌，`AfterCardPlayed` 与上一张比颜色。`PowerInstanceType.Instanced`。`AfterSideTurnEnd` 移除并回滚。参考 `NamelessYoukaiPower`。

#### Power 多人按施放者分实例

- 默认 `PowerInstanceType.None`：同一目标共享单个实例，多玩家施放时层数叠在一起、`Applier` 只记**第一个**施放者（`PowerCmd.Apply` 仅新建时 `power.Applier = applier`，后续叠加只走 `ModifyAmount`）。若逻辑按 `Applier` 判定，多人会失效（如怨仇 `YuanChouPower`）。
- 需按玩家分别计算：重写 `public override PowerInstanceType InstanceType => PowerInstanceType.InstancedPerApplier;`（`MegaCrit.Sts2.Core.Entities.Powers`）。叠加时会 `target.GetPowerInstances(Id).FirstOrDefault(p => p.Applier == applier)`，每个施放者各自图标与层数。参考 `YuanChouPower`。
- 带来源的本地化：`description`/`smartDescription` 用 `[gold]{Applier}[/gold]` 指名（如「对[gold]{Applier}[/gold]造成的伤害降低…」）；他人视角用 `.remoteDescription`（如「由于[gold]{Applier}[/gold]的怨仇…」，参考原版夹击 `FLANKING_POWER.remoteDescription`），同样支持 `{Amount}`。三套语言文件需同时维护。

#### Power 再次施加（叠加）时的再触发

- `PowerModel.AfterApplied`（以及 `BeforeApplied`）**只在 Power 首次附着到目标时触发**。源码注释明确写了「Does not run if the owner already has this power, and its amount was just changed.」：`PowerCmd.Apply<T>` 先用 `FindExistingInstanceForStacking` 查已有实例，命中则只走 `PowerCmd.ModifyAmount` 叠加层数，`AfterApplied` 不再执行。
- 需要「每次施加都再触发一次」时，改写 `AfterPowerAmountChanged(PlayerChoiceContext, PowerModel power, decimal amount, Creature? applier, CardModel? cardSource)`（`MegaCrit.Sts2.Core.Models.AbstractModel`）。首次施加传施加量、叠加传增量，两种路径都会调用。
- `amount` 是**本次增减量，不是剩余层数**（首次为 `modifiedAmount`，叠加为 `modifiedOffset`，可能为负）。要先 `if (power != this) return;` 过滤，再 `if (amount <= 0m) return;` 排除层数被消耗/移除的情况，然后按 `-amount` 结算，避免总量被重复结算。
- 参考实现：`GeishehuaxiaojiejianshaoliliangPower`（首次施加扣力量，再次施加按增量继续扣）。原版参考 `ViciousPower`、`PossessStrengthPower`。

### 7.5 怪物随机外观

重写 `CreateCustomVisuals()`，用 `base.Rng`（不要 `GD.Randf`）。每个外观单独 tscn，各自把 Sprite 锚点烘在贴图底部。参考 `FantasyMushroomMonster`。

### 7.6 怪物偷牌（SwipePower 模式）

`IWillReturnItPower`：`InstanceType.Instanced` + `StackType.Single`，每张被偷牌一个实例。归还时 `GetPowerInstances<T>()`。动画：场景 `%StolenCardPos`，`NCard.Create` 挂到 Marker2D，`LocalContext.IsMine`。归还 `NCard.FindOnTable(card)?.QueueFreeSafely()`。

位移只 Tween `Visuals.GetCurrentBody()`，记录并恢复 `bodyOrigin`（魔理沙 body 初始不是 0）。携带物挂到 body 下并按 scale 反算。特效 `GD.Load<PackedScene>` 挂 `CombatVfxContainer`。震屏 `NGame.Instance?.ScreenShake(...)`。极限火花场景当前在 `res://images/sprite/marisa/masterspark.tscn`。

紫苑厄运字符：场景 `res://images/sprite/shion/shion_negative_burst.tscn`。字符是同一张图集 `shot_negative_001.png`（256×256）的 4 个 128×128 区域（2×2）。根节点挂 `scripts/Vfx/NShionNegativeBurstVfx.cs`（一次性爆发，`_Ready` 自动播放，播完 `this.QueueFreeSafely()` 自删）。通过 `NShionNegativeBurstVfx.Create(origin, count, scatterRadius)` 创建，内部动态设置 `GpuParticles2D.Amount`（总粒子数）和 `ParticleProcessMaterial.InitialVelocityMin/Max`（散射初速度，通过 `particles.ProcessMaterial as ParticleProcessMaterial` 访问），挂 `CombatVfxContainer`。**每颗粒子随机一个字符（混合出现）同样走图集动画随机帧**（`CanvasItemMaterial` 2×2 + `anim_offset_min=0` + `anim_offset_max=1` + `anim_speed=0`）。厄运播撒、雁过拔毛命中后在玩家 `VfxSpawnPosition` 生成；绝对输家分两波大量播撒。

女苑财富字符：场景 `res://images/sprite/joon/joon_wealth_burst.tscn`。字符是同一张图集 `shot_wealth0000.png`（256×256）的 4 个 128×128 区域（2×2）。根节点挂 `scripts/Vfx/NJoonWealthBurstVfx.cs`（持续发射型，`Start()` 发射 / `Stop()` 停止并延迟自删）。通过 `NJoonWealthBurstVfx.Create(pos)` + `AddChild` + `Start()` 使用，挂 `BackCombatVfxContainer`（角色身后层）。**每颗粒子随机显示一个字符（混合出现）通过纯配置实现**：单个 `GPUParticles2D`，纹理用整张图集，`CanvasItemMaterial.particles_animation=true` + `particles_anim_h_frames=2` + `particles_anim_v_frames=2` + `particles_anim_loop=false`，`ParticleProcessMaterial.anim_offset_min=0` + `anim_offset_max=1`（每颗粒子随机起始帧）+ `anim_speed_min/max=0`（不播放动画，固定随机帧）。

粒子图集动画模式（参考原版 `vfx_sandy_impact` / `vfx_thought_bubble`）：必须用 `GPUParticles2D`（原版图集动画特效都用它，`CPUParticles2D` 对 `process_material` 的 anim 参数支持有限）。运动参数（gravity / velocity / spread / scale / color_ramp / anim_*）全部放 `ParticleProcessMaterial`，节点上只有 `amount` / `texture` / `material` / `process_material` / `emitting` / `one_shot`。scale 用 `scale_min/max` + `scale_curve`（`CurveTexture`），color 用 `color_ramp`（`GradientTexture1D`），与 `CPUParticles2D` 的 `scale_amount_*` / 节点平铺属性不同。GPU 粒子动态改参数：`Amount` 直接设节点属性，初速度等 material 参数通过 `((ParticleProcessMaterial)node.ProcessMaterial).InitialVelocityMin/Max` 设置（参考原版 `NThinSliceVfx`）。

自管 VFX 脚本模式（参考原版 `NBigSlashImpactVfx`）：`partial class ... : Node2D` + `const ScenePath` + 静态 `Create()`（走 `PreloadManager.Cache.GetScene(ScenePath).Instantiate<T>()`，比 `GD.Load` 静态缓存更贴近原版，未预注册路径会 fallback 即时加载并记 `_missedCacheAssets`）+ `_Ready` 里 `TaskHelper.RunSafely(PlaySequence())` 自播自删。注意：粒子 `Lifetime` 是 `double`，`Mathf.Max` 需 `(float)` 强转；扩展方法 `QueueFreeSafely` 无接收者调用会 CS0103，需写 `this.QueueFreeSafely()`。子节点收集需在 `_Ready` 后（`Create` 时 `GetChildren()` 为空），参数先存字段、`_Ready` 里再配置。VFX 脚本随机用 `GD.Randi()` 纯随机（不占用游戏 `Rng` 随机数流）。

魔理沙星星弹幕：场景 `res://images/sprite/marisa/marisa_stellar_stars.tscn`，脚本 `scripts/Vfx/NMarisaStellarStarsVfx.cs`（`Create(origin, starCount)` 一次性齐射自删）。**高速直线飞行粒子**：`ParticleProcessMaterial.direction = Vector3(-1,0,0)`（发射朝向）+ `spread` 小角度（如 8°）+ `initial_velocity_min/max = 2000~2600`（超高速）；**粒子自身旋转**用 `angular_velocity_min/max`（如 ±1440°/s）+ `angle_min/max = -180~180`（初始朝向随机），旋转不需要额外贴图帧；`scale_curve`（CurveTexture 线性衰减）让星星飞行中缩小、`color_ramp`（GradientTexture1D 末段透明）淡出。怪物端：`4 + (int)(GD.Randi() % 5u)` 生成 4~8 数量（GD.Randi 纯随机不占游戏 Rng 流），`creatureNode.VfxSpawnPosition` 为发射原点，挂 `CombatVfxContainer`。

魔理沙瓶子抛射：场景 `res://images/sprite/marisa/marisa_bottle.tscn`，脚本 `scripts/Vfx/NMarisaBottleVfx.cs`。**抛物线 + 持续旋转的节点型飞行物**（参考原版 `NItemThrowVfx` 手写飞行循环而非 GPU 粒子）：`Sprite2D`（Bottle）负责旋转表现（`_bottleSprite.RotationDegrees = t * TotalSpinDegrees` 全程转过固定总角度），GPUParticles2D（Trail，`emitting=false` + `amount` + `one_shot=false` + 短 `lifetime`）作拖尾。飞行循环 `TaskHelper.RunSafely(Fly())`：`while (elapsed < FlightTime)` 内 `float t = elapsed/FlightTime`，**水平匀速 + 垂直正弦弧线** `GlobalPosition = source.Lerp(target, t) - Vector2.Up * (Mathf.Sin(t * Mathf.Pi) * ArcHeight)`（弧顶高 ArcHeight），用 `GlobalPosition` 赋值避免容器原点偏移影响；计时用 `float delta = await this.AwaitProcessFrame()`（`MegaCrit.Sts2.Core.Nodes.GodotExtensions`，返回真实帧间隔，不能用 `GetProcessDeltaTime()`——VFX 节点没开 `_Process` 会返回 0 卡死）。到达落点后 `_trail?.SetEmitting(false)` 停拖尾并触发 `Arrived` 事件（调用方播放命中特效），`_cts`（CancellationTokenSource）在 `_ExitTree` 取消防泄漏。**攻击结算后精确销毁**：怪物端把 `bottleVfx` 存引用，`await DamageCmd.Attack(...)` 完成后 `bottleVfx.QueueFreeSafely()`；命中特效 `NKinPriestGrenadeVfx.Create(target)` 独立挂到玩家 `GetVfxContainer()` 不受瓶子销毁影响（不要把命中特效做成瓶子的子节点）。飞行起点用 `creatureNode.VfxSpawnPosition`、落点取 `targetNode.VfxSpawnPosition`（多人取最左侧玩家 `GlobalPosition.X` 最小）。

卡片/Power 播放自管 VFX：`NCombatRoom.Instance?.GetCreatureNode(creature).VfxSpawnPosition` 获取单位特效出生点（玩家/敌人通用）；持续型（女苑 `NJoonWealthBurstVfx`）用 `Create(pos)` + `AddChild` + `PlayForSeconds(秒)`（内部 Start 后定时 Stop 自删），短暂"背后浮现"挂 `BackCombatVfxContainer`（角色身后层），命中类挂 `CombatVfxContainer`；一次性爆发（紫苑 `NShionNegativeBurstVfx`）用 `Create(pos, count, scatterRadius)` + `AddChild`（`_Ready` 自动播放自删）。Power 的 `BeforeSideTurnEnd` 里可遍历 `CombatState.HittableEnemies` 对每个敌人播一次（不要放进施加 buff 的循环里，避免重复）。

### 7.13 通用卡牌流光系统（`CardGlowPatch`）

`scripts/Patches/CardGlowPatch.cs`：注册式的「让某些手牌显示流光」框架，各功能模块只声明
「什么牌该发光 + 用哪个 shader」，UI 侧统一处理。

```csharp
CardGlowPatch.Register(new CardGlowStyle
{
    Id = "TouhouAncients.NamelessYoukai",
    ShaderPath = "res://shaders/nameless_youkai_flow.gdshader",
    Predicate = card => /* 是否命中 */
});
```

- 每条 `CardGlowStyle` **独占一个 shader 文件**（`res://shaders/xxx.gdshader`），实现放在
  `Predicate` 里；同一张牌命中多个样式时取**先注册**的那个。
- 内置样式在 `CardGlowPatch` 的**静态构造函数**里注册：任何对 `CardGlowPatch` 静态成员的首次访问
  （`Register` / `GetStyleFor`，以及 Harmony 补丁内部的调用）都会触发静态构造，因此内置样式
  必定在第一次使用前完成注册，无需 `Entry.Init()` 显式调用。
- 底层两条补丁：
  1. Postfix `CardModel.ShouldGlowGold` getter → 命中的牌进入原版高亮分支（原版 UI 依赖它决定是否 `AnimShow`）。
  2. Postfix `NHandCardHolder.UpdateCard` → 把命中牌的高亮 `Material` 换成该样式的流光材质，
     并同步私有字段 `NCardHighlight._shaderMaterial`（`AnimShow/AnimHide` 的 tween 每帧对它 `SetShaderParameter("width", ...)`）。
- **坑 1**：原版高亮分支要求 `card.CanPlay()`，否则走 `AnimHide()`。若希望「费用不足也保持发光」
  （如命运标记牌），Postfix 里要主动 `highlight.AnimShow()` 覆盖。
- **坑 2**：还原默认材质时**只还原本系统替换过的牌**（按 `FlowMaterials` 里缓存的材质引用判断），
  否则会把原版金光或其它 mod 的自定义材质一起清掉。
- **坑 3**：不要每次 `UpdateCard` 都重设材质 —— `AnimShow()` 会 `Kill()` 上一个 tween，
  反复调用会让高亮一直停在起始值（视觉上不发光）。样式未变时直接 `return`。
- **刷新时机**：标记状态变化（回合开始打标 / 打出牌去标 / 战斗结束清标）后必须调用
  `CardGlowPatch.RefreshHandCard(card)`，否则流光与额外文本要等下一次手牌重排才更新。
  内部走 `NCard.FindOnTable(card, PileType.Hand)` → 父节点 `NHandCardHolder.UpdateCard()`。
- 每个样式的 shader 首次使用时惰性 `GD.Load`，材质按「高亮节点 × 样式」各建一份实例
  （shader 参数互不干扰）。缓存用 `ConditionalWeakTable`，节点销毁后自动回收。

### 7.14 「命运」标记的卡面呈现（`FatePendant` + `FateMarkPatch`）

`scripts/relics/Remilia/FatePendant.cs` + `scripts/Patches/FateMarkPatch.cs`
（搭配 `res://shaders/fate_blood_mist.gdshader` 血色流光）。

- **标记不写 static**：标记集合是遗物实例的私有字段（`HashSet<CardModel>`），
  多人模式下每个玩家各持一个遗物实例，static 会让各玩家互相覆盖。
  For 克隆（读档 / 多人同步复刻）必须 `protected override void AfterCloned()` 里重建集合 ——
  `MemberwiseClone` 会复用同一集合引用，不重建会让副本与原实例共享标记。
- **遗物没有 `InitInternalData`**：那只存在于 `PowerModel`。遗物侧的私有运行时状态
  一律用「实例字段 + `AfterCloned` 重置 + `BeforeCombatStart`/`AfterCombatEnd` 清理」。
- **从卡牌反查遗物**：`card.Owner?.GetRelic<FatePendant>()`（`Player.GetRelic<T>()`）。
  发光补丁与文本补丁都靠它拿实例，因此不需要任何静态查询入口。
- **额外卡牌文本**：原版的额外文本通道（`Enchantment/Affliction.DynamicExtraCardText`）
  是附魔/苦恼独有的虚属性（`HasExtraCardText`），对普通 `CardModel` 不开放；关键词则走
  `Keywords` 集合 + `CardKeywordOrder`。BaseLib 的 `DescriptionOverrides` 就是官方为
  「想做关键词式效果、但不想真的占一个关键词」预留的入口（其源码注释原文：
  *These are intended for mods that add new keyword-like effects that don't necessarily work as actual keywords.*），
  BaseLib 自己的 `CardModifier.ModifyDescription/ModifyDescriptionPost` 内部也用它。
  两个事件的区别只在插入位置：
  - `CustomizeDescription`（**前置**）：注入「基础描述」字符串本身，结果是
    `[前置关键词]\n基础描述\n额外文本\n[后置关键词]`——**与附魔额外文本位置一致**。
  - `CustomizeDescriptionPost`（**后置**）：在 `list2` 整体 `Join` 之后追加，会排到**所有关键词之后**。
  拼接样式与附魔相同：`description += "\n[purple]文本[/purple]"`。
  **订阅必须由 `Entry.Init()` 显式调用初始化方法**，不能写在静态构造函数里
  （Harmony 不会触发带 `[HarmonyPatch]` 的类的静态构造，订阅会静默失效）。
- **额外 HoverTip**：Postfix `CardModel.HoverTips` getter，`__result.Concat([new HoverTip(title, desc)])`。
  描述里若有 `{Energy}` 之类占位符，要 `relic.DynamicVars.AddTo(desc)` 注入后才会渲染。
- **「首张牌」判定**：`CombatManager.Instance.History.CardPlaysFinished` 在
  `Hook.AfterCardPlayed` **之前**就已写入 `CardPlayFinished`，所以在遗物的 `AfterCardPlayed` 里
  `Count(e => e.CardPlay.Player == Owner && e.HappenedThisTurn(Owner.Creature.CombatState)) == 1`
  即表示刚打出的正是本回合第一张。
- **隐藏效果（至少一张可打出）**：先从 `CanPlay() == true` 的手牌中抽 1 张，
  再从剩余手牌补齐余下张数；全部不可打出时退化为纯随机。随机用
  `player.RunState.Rng.CombatCardGeneration`（与其它遗物一致，保证多人同步）。
- 回合开始若手牌不足 `{Cards}` 张，按实际张数标记（`Math.Min`）。

蝙蝠剪影（`shaders/fate_blood_mist.gdshader` + `shaders/bat.png`）：

- **只取 alpha 当遮罩**：贴图是「黑剪影 + 透明背景」，shader 只采样 `.a`，颜色一律由
  `bat_color` 决定。因此换成白色剪影也一样能用，不需要改 `bat.png.import` 的任何设置
  （当前 `compress/mode=0` + `mipmaps/generate=false`，shader 侧也只用 `filter_linear`、不采 LOD）。
- **越界采样必须在 shader 里显式截断**：`repeat_disable` 的越界采样会被钳到边缘像素，
  而 bat.png 的边缘像素恰好落在翅膀上（alpha 非 0），不截断就会把翅膀最外侧那列
  "拉丝"成一条横带。`sample_bat()` 用 `step()` 把出界一律当 0 —— 换贴图时要保证四周
  留一圈全透明边距（现图 x 留 2px、y 上下留 84/68px）。
- **贴图在场景里绑定**：`fate_mark.tscn` 新增 `bat.png` 的 ext_resource 并写进
  `shader_parameter/bat_texture`。靠场景依赖关系即可随 PCK 导出（export_filter 是
  `all_resources`），不必再进预加载清单，也不需要 C# 侧 `SetShaderParameter`。
- **振翅只能靠形变**：贴图是固定姿态，`bat_warp()` 把采样点绕 `bat_pivot`（肩部铰链，
  等比例坐标、相对贴图中心）旋转，等价于翅膀绕肩扇动。躯干（`|x| < bat_body_half`）
  角度为 0 不跟着扭，向内到外由 `smoothstep` 抬到满角度；左右两侧各取 ±flap 保证对称。
- **辉光不再有距离场**：原来是程序化 SDF 才能写 `exp(-d*45)`；改用贴图后改为绕当前像素
  取 12 个样本求平均（环形模糊），用「模糊值 − 剪影值」近似由内向外衰减的辉光，
  `bat_glow_width` 控制扩散半径。形状本身不再需要 `fwidth` 抗锯齿 —— 走线性过滤。
- **默认值是按 bat.png 量出来的**：贴图内容占 0.98 × 0.41，`bat_size = 0.44` 对应约
  0.43 卡宽翼展；`bat_offset = (0.002, -0.024)` 补掉图里蝙蝠略偏下的位置。换贴图后
  这三个值（外加 `bat_pivot`、`bat_body_half`）需要重新量一遍。

#### 伤害转移（ModifyUnblockedDamageTarget）

原版 `InterceptPower`（拦截）绑定玩家 `Player.NetId`，**怪物不可用**。给怪物用的伤害转移用 `ModifyUnblockedDamageTarget`（原版 `DieForYouPower` 模式）：

```csharp
public override Creature ModifyUnblockedDamageTarget(Creature target, decimal amount, ValueProp props, Creature? dealer)
{
    if (target != base.Owner) return target;          // 只拦截对持有者的攻击
    if (base.Owner.IsDead) return target;
    if (!props.IsPoweredAttack()) return target;      // 仅攻击牌伤害（毒/灾厄不转移）
    if (被转移目标 == null || 被转移目标.IsDead) return target;
    return 被转移目标;
}
```

- 持续时间：`AfterSideTurnStart(CombatSide side, ...)` 中按侧移除。施放发生在敌人回合 → 当次 `Enemy` 侧 `AfterSideTurnStart` 已过，因此在 `side == CombatSide.Enemy` 时 `PowerCmd.Remove(this)` 正好是"下一个敌人回合开始"移除（持续 1 个完整回合）。参考 `GuardingPower`
- 注意 §5.8：`participants` 只含当前行动方，敌人侧的 Power 在玩家回合时 Owner 不在 participants 里，勿用 `participants.Contains(Owner)` 判断

#### 动态意图（StatusIntent 层数）

`StatusIntent(int count)` 的 `CardCount` 是只读的，但 `GetIntentLabel` / `GetIntentDescription` 是 `virtual`。层数动态变化的意图可继承 `StatusIntent`，在显示时重新读取层数：

```csharp
public sealed class LingLingPoisonIntent : StatusIntent
{
    public LingLingPoisonIntent() : base(1) { }
```

### 7.15 「离开梦境」：哆来咪 → 涅奥房间（逐玩家事件实例替换 + 场景溶解）

哆来咪事件末尾追加的第 4 个选项，效果是**放弃哆来咪的遗物、改为进入涅奥的房间**，
且**逐玩家独立**：只影响点它的那个玩家，其他玩家仍留在哆来咪的选项页选自己的遗物。

相关文件：

| 文件 | 职责 |
|------|------|
| `scripts/ancients/LeaveDream/LeaveDreamReentry.cs` | 选项构造、事件实例替换、单人存档、房间订阅转移 |
| `scripts/ancients/LeaveDream/LeaveDreamSequence.cs` | 演出：哆来咪台词 → 等「继续」→ 切换场景 |
| `scripts/ancients/LeaveDream/NLeaveDreamDissolve.cs` | 溶解覆盖层（房间截图 + 原版 dissolve 着色器） |
| `scripts/Patches/LeaveDreamPatches.cs` | 回血拦截、完成时存档、对话推进、涅奥选项空列表兜底四个 Harmony 补丁 |
| `scripts/Patches/LeaveDreamSaveGuardPatch.cs` | 存档兜底：别人存档把「待恢复房间」写空时，按当前状态补回正确的涅奥/先古房 |

**为什么不用「压房间」**：`RunManager.EnterRoomWithoutExitingCurrentRoom` 是全局操作，
多人下必须所有端同时执行，会把全队的事件一起换成涅奥，做不到「互不影响」。

**做法（逐玩家替换事件实例）**：`EventSynchronizer._events` 是「每个玩家一份 mutable 事件实例」的列表，
非共享事件下各端 UI 绑定的是自己那一份（`EventSynchronizer.GetLocalEvent()`）。
所以只要把**选择者槽位上的实例**换成新的 `Neow` mutable 实例，就能只影响他一个人。要点：

1. 换入前先把被替换的旧实例 `EnsureCleanup()` 掉（清掉它对已释放节点/回调的引用）。
2. `EventModel.BeginEvent(player, combatSynchronizer, isPreFinished)` 的真实签名带战斗同步器
   （工作区源码树里是两参版本，以实际 DLL 为准），从 `EventSynchronizer._combatSynchronizer` 反射取来传入。
3. 换入的实例必须**手动补上 `EventRoom.OnEventStateChanged` 订阅** —— 该方法决定了「全员完成即把房间标记
   pre-finished 并保存」；漏了它，当该玩家是最后一个完成时不会触发存档，多人读档回来就不是「只剩继续」的 DONE 页。
4. 选项广播通道天然承担了同步：非共享事件点击选项会执行 `ChooseOptionForEvent(本人, 索引)` 并广播
   `OptionIndexChosenMessage`，各端收到后对同一份实例再跑一遍，于是他在涅奥房间里的每次选择都会在所有端复现。
   非共享事件房间退出时会 `GenerateChecksum`，状态分叉会被判定为 `StateDivergence` 并断开客户端，
   因此**不能**改用「只在本端新建的本地事件实例」。
5. 单人存档：进入涅奥视图时 `SaveManager.Instance.SaveRun(new EventRoom(ModelDb.Event<Neow>()))`，
   读档回到涅奥房间；`AncientEventModel.Done()` 后再存一次「已 `MarkPreFinished()` 的涅奥房间」，
   读档只剩「继续」。多人不写任何存档（多人读档一定会回到哆来咪的事件房，是既有行为）。

**与遗物互斥**（绝不会既拿哆来咪遗物又拿涅奥遗物）：不需要任何「已触发过」的持久标记。
未全员完成时的存档发生在进入先古房间那一刻，里面既没有哆来咪遗物、也没有「离开梦境」的选择记录，
读档等于整段回退、可以自由重选；全员完成时 `EventRoom.OnEventStateChanged` 会把房间标记 pre-finished
并保存，读档只剩「继续」。两条路径都不可能同时拿到两边的遗物。

**回血拦截**：`LeaveDreamHealSuppressPatch` 的条件是 `this is Neow` 且
`Owner.RunState.Act.Ancient is TouhouAncientBase { ShowAct: 1 }`（本幕抽中的是本 Mod 的一层先古之民，
却进入了涅奥房 —— 只可能来自本功能；该条件不依赖运行期标记，所以读档重建涅奥房间时同样生效）。
注意 `BeforeEventStarted` 返回 `Task`，Prefix 跳过时必须显式 `__result = Task.CompletedTask`，
否则调用方 `await` 到 null 会抛空引用。

**溶解演出**：先把当前画面（哆来咪房间 + 那句字幕）用 `Viewport.GetTexture().GetImage()` 截成贴图
（需先 `await` 根视口的 `RenderingServer.FramePostDraw`），铺满屏幕盖在涅奥房间之上，
再用原版溶解着色器 `res://shaders/dissolve.gdshader`（怪物死亡风化同一套）把 `threshold`
从 1 补间到 0（用 `TweenMethod` 直接改材质参数，不用属性路径补间），渐隐后露出下面的涅奥房间。
截图失败或着色器加载失败时退化为「旧房间逐渐淡出」的交叉淡化，保证始终有过渡。

> **踩过的坑（2026-09-24）**：把整棵 `NEventRoom`（Control 树）`Reparent` 进 `SubViewport`、
> 再用 ViewportTexture 显示的做法实测**拿不到可见输出** —— 玩家会直接看到涅奥房、毫无过渡。
> 另外注意：台词内容是**从下方滑入的 1 秒补间**，而推进热区覆盖面很大，
> 玩家在滑入期间随手一点就会跳过台词——所以滑入期间要主动关掉热区（`%DialogueHitbox`）。

**对话推进的挂接方式**：不要自己去找热区节点，而是给 `NAncientEventLayout` 的私有方法
`OnDialogueHitboxClicked` 加 Harmony Postfix（原版推进逻辑本来就挂在它的 `Released` 信号上）；
补丁只在「本功能正在等推进」时才通知演出继续，其它对话完全不受影响。

**涅奥选项为空（本局带 modifier 时只剩「继续」）**：`Neow.GenerateInitialOptions()` 是二选一的岔路 ——
`RunState.Modifiers` 为空则正常掷 3 个选项；非空则只收集各 modifier 自己提供的涅奥选项
（`ModifierModel.GenerateNeowOption`，基类默认返回 null），一个都没有时 `return Array.Empty<EventOption>()`。
空列表会让 `AncientEventModel.SetInitialEventState` 直接 `StartPreFinished()`：事件当场判为已完成，
界面只剩 PROCEED（也就是「继续」），祝福一个都拿不到。
原版自己碰不到这条空路径：涅奥只出现在第一幕第一间房，而第一间房的选项是在
`EventRoom.EnterInternal → EventSynchronizer.BeginEvent` 里生成的，之后才跑 `Hook.AfterRoomEntered`；
而「带 run modifier 但没登记在 run 里」的 mod 正是那时才把 modifier 写进去的
（例：海克斯符文的 Mayhem 在 `OnRoomEntered` 里补挂，日志可见
`recovered missing modifier room=EventRoom ... reattaching`）。
「离开梦境」是在**第一间房之内**才新建涅奥，那时 modifier 已经登记 → 必然踩空，单机/联机表现相同。
兜底见 `LeaveDreamNeowOptionsPatch`（`Neow.GenerateInitialOptions` 的 Postfix）：只在
「结果为空 + 是本功能重进出来的涅奥（`LeaveDreamReentry.IsReentryNeowRoom`）+ 本局 modifier 表非空」
三个条件同时满足时，临时把 `RunState.Modifiers` 换成空表（反射 `set_Modifiers`，取不到退回
`<Modifiers>k__BackingField`）再调一次原版方法（用 `[ThreadStatic]` 重入标记挡住递归），
`finally` 里立刻换回，于是原版走「没有 modifier」那条正常岔路掷出标准三选一。
modifier 自己提供了涅奥选项时（原版 Draft / Sealed Deck / Insanity / All Star / Specialized）结果非空、
完全不介入；反射解析失败也只打错误日志、维持现状。
带 Modifier 的局里「离开梦境」本来根本不提供（见 7.17），所以这条兜底踩到的只有两种情况：
「标准局 + 第三方 mod 在进房后中途补挂 modifier」，以及"本局只有不提供涅奥选项的隐形 Modifier"时
哆来咪回落到正常选项、于是又能选「离开梦境」的那一种局（Zone the Spire 等；此时该 mod 自己给
`Neow` 打的隐藏补丁会让结果非空，本条兜底同样不介入）。

**存档被第三方写空（读档回到先古初始页、已获得的遗物保留）**：读档进哪间房**只**由存档里的
`pre_finished_room` 决定（`RunManager.EnterMapPointInternal`：非 null 就进那间房，null 就
`CreateRoom(roomType, pointType)` 按 `Act.Ancient` 重建）。所以这个字段一旦被写成 null，读档就会重建出
一间**全新的先古房**，而玩家进度（遗物、牌、金币）都在 run state 里保留着 → 可以反复拿。
2026-09-26 用临时的 `[SAVE-TRACE]` 追踪补丁（定位完成后已删除）抓到具体过程：原版 `EventRoom.OnEventStateChanged` 先写下
`Event:DOREMY(preFinished)`，紧接着
`HextechRunes.HextechRuneSelectionCoordinator.PersistActSelection`（选完符文后）调用
`SaveManager.Instance.SaveRun(null, saveProgress: false)`，`RunManager.ToSave(null)` 把该字段置空，
把正确状态覆盖掉。单机、联机都会中（联机还会顺带破坏「全员完成才存档 → 读档不能刷遗物」那条保证）。
为什么「先古一开始就是涅奥」看起来没事：重建出来的涅奥因为「本局有 modifier → 原版给不出选项」而
**瞬间 finished**，于是 `EventRoom.EnterInternal` 里那行
`if (@event.IsFinished && !IsPreFinished) OnEventStateChanged(@event)` 立刻把房间标成 pre-finished
并把存档补写正确（追踪里能看到这一笔）；哆来咪的选项与 modifier 无关、永远不会 finished，
所以没有这层「巧合自愈」。
兜底见 `LeaveDreamSaveGuardPatch`（`SaveManager.SaveRun(AbstractRoom?, bool)` 的 Prefix，用 `ref`
直接改实参 —— 只决定这一笔存档写什么，不额外补存、不会递归）：调用方没带待恢复房间时按当前状态填上 ——
① 本地事件实例是重进出来的涅奥 → 涅奥房（`IsFinished` 则标 pre-finished）；
② 当前房间是已 pre-finished 的先古 `EventRoom` → 原样恢复（多人同理，代表全员已完成）。
两者都不满足就完全不介入（进新节点、开新局、正常游玩中的存档照旧）。
**已知边界（按约定不处理）**：已经被写坏的旧存档不会因此被修好 —— 读它仍会重建全新先古房、
那一局多给一次选择；但从那一刻起每一笔存档都会被这里纠正回正确状态。

### 7.16 怪物台词气泡（`TalkCmd.Play`）

怪物台词**没有**原版自动播放机制（`MoveState` 不接收台词参数），必须在代码里手动调用：

```csharp
using MegaCrit.Sts2.Core.Localization;   // LocString
using MegaCrit.Sts2.Core.Nodes.Vfx;      // VfxColor / VfxDuration

private static readonly LocString _line =
    new LocString("monsters", "TOUHOUANCIENTS-XXX_MONSTER.moves.MOVE_KEY.banter");

// 播放点（通常是技能方法开头，或"切换意图"的触发点）
TalkCmd.Play(_line, base.Creature, VfxColor.White);
```

- 签名：`TalkCmd.Play(LocString line, Creature speaker, VfxColor vfxColor, VfxDuration duration = VfxDuration.Custom)`。
  不传 `duration` 即 `Custom`：按 `GetRawCharCount`（剥掉 bbcode、空格、换行后的字符数）× 0.12 秒计算气泡时长，最快 0.5 秒。
  固定时长档位：`VeryShort` 1.0 / `Short` 1.5 / `Standard` 1.75 / `Long` 2.25 / `VeryLong` 3.0 秒。
- `VfxColor` 取值：`Red` / `Green` / `Blue` / `Purple` / `Black` / `White` / `Cyan` / `Gold` / `Orange` / `Swamp` / `DarkGray`。
- 说话者已死亡时 `TalkCmd.Play` 直接返回 null（`speaker.IsDead` 检查）；死亡时仍需播报要绕过它（见 `YorigamiJoonMonster`）。
- 本地化键沿用 `TOUHOUANCIENTS-{MONSTER}_MONSTER.moves.{MOVE_KEY}.banter`；多条时加 `banter1/2/3`（`YorigamiShionMonster` 等有先例）。
  jpn 与 eng 内容一致（jpn 用英语填充），见 §"翻译基准线"。

**播放点选择**：放在"共享的触发方法"里可以顺带得到条件限定，不必额外写判断。
例：灵梦梦想天生台词放在 `HakureiReimuMonster.ForceDreamNatureNext()` 开头 —— 该方法**只被**
`IndiscriminateSubjugationPower.TryTrigger()` 调用，战斗开场那个固定的第一回合梦想天生走
`AfterAddedToRoom()` + 状态机初始状态、不经过它，于是"第一回合不播、只由无差别降伏触发"是方法调用图自带的性质。

### 7.17 带 Modifier 的局：第一幕先古之民整页只给 Modifier 选项

**坑**：`Neow.GenerateInitialOptions`（`Neow.cs:216` 起）是 if/else 二选一 —— `RunState.Modifiers` 为空才掷
「2 个祝福 + 1 个诅咒遗物」的三选一；非空则**整页**换成各 Modifier 的 `GenerateNeowOption` 选项
（一个都不提供时空表 → `StartPreFinished()`，只剩「继续」）。也就是说：

- **涅奥是第一幕第一间房里唯一发放 Modifier 奖励的地方**：`GenerateNeowOption` 全原版只有 `Neow.cs:288`
  一个调用点，`NeowOptionTitle` / `NeowOptionDescription` 也只有 `Neow.cs:292` 一处使用；
- 原版敢把它写死在涅奥类里，是因为原版第一幕先古之民**恒为涅奥**：`Overgrowth.cs:26` / `Underdocks.cs:26`
  的 `AllAncients` 是硬编码单元素列表，二三幕才有 3 个候选（`Hive.cs:24` / `Glory.cs:23`）。

而 `ShowAct == 1` 的本 Mod 先古之民与涅奥同池（§1.2）：抽到哆来咪时那些奖励原本永远不会发放，其中
Draft / SealedDeck / Insanity 的 `ClearsPlayerDeck` 还会先在 `ModifierModel.OnRunCreated` 把初始牌组清空 →
玩家**开局一张牌都没有**。（`RunManager.InitializeNewRun()` 跑 `OnRunCreated`，它在 `GenerateRooms()` 之前，
所以事件选项生成时 `RunState.Modifiers` 已有值、牌组也已经清空。）

**做法**：不新增补丁，`TouhouAncientBase.GenerateInitialOptions` 最前面加一道与涅奥同构的分支：
`ShowAct == 1 && Owner.RunState.Modifiers.Count > 0` 时**整页只返回 Modifier 选项链的第一个**；链为空时再看
`RunState.GameMode != GameMode.Standard`：每日 / 自定义挑战返回空表、与原版一样当场判完成，
标准局（`GameMode.Standard` 却有 Modifier —— 只有调试或第三方 mod 会造出这种局）落回下面的正常遗物选项页。

- `BuildRunModifierOptions` 照 `Neow.ModifierOptions` 逐个问 Modifier 要 `GenerateNeowOption`（标题 / 描述 /
  HoverTip / textKey 取 `NeowOptionTitle` / `NeowOptionDescription` / `HoverTips` / `Id.Entry`）；
  `OnRunModifierOptionChosen` 照 `Neow.OnModifierOptionSelected` 推进：先发奖 → `SetEventState(InitialDescription,
  [下一个])` → 最后一个用 `Done()` 收尾（比 `SetEventFinished` 多一步跑步历史记录）。`SetEventState` 与 `Done`
  都是 `protected`，但都在本类内部调用，**不需要反射**。
- **这时不摆哆来咪的遗物选项，也不摆额外选项「离开梦境」**：带 Modifier 的局里她表现为"只有 Modifier 选项
  的一页"，与原版涅奥完全一致，也不会出现"既拿遗物又拿 Modifier"（链为空的那一种局除外，见末段）。
- **没有 Modifier 的局**（标准局、没勾 Modifier 的自定义挑战）走原逻辑：3 个遗物选项 + 挑战选项 +
  「离开梦境」，与改动前逐字相同。
- 发奖函数读 `eventModel.Rng`（`AllStar` / `Insanity` / `Specialized`）：用本事件实例的 Rng
  （`EventModel.BeginEvent` 里非共享事件 = `runSeed + 玩家槽位 + hash(事件 Id)`，各端一致、逐玩家独立）。
- **发奖异常不兜**（与 `Neow.OnModifierOptionSelected`、四季映姬逐字一致）：异常会穿出 `EventOption.Chosen`
  —— 它已经把 `WasChosen` 置位，而这类选项 `DisableOnChosen` 为 true，所以按钮再点会**静默返回**（连 handler
  都不进），页面停在「选项已置灰又没有新选项」上、只能读档重来（`EventRoom` 存档只记事件与 `IsPreFinished`，
  不记 `WasChosen`，读档重建事件实例）。这是刻意的取舍：不替第三方 Modifier 的 bug 兜底。异常不会不见 ——
  `EventSynchronizer.ChooseOptionForEvent` 用 `TaskHelper.RunSafely` 起这个任务，那里先 `Log.Error` + Sentry
  再把任务留成 faulted（最终由 `AwaitPendingOptionTasks` 的 `Task.WhenAll` 吃掉，所以不会因此崩游戏或卡房间流程）。

**顺带确认过的事**：原版**每日挑战的涅奥那一页本来就没有祝福** —— Modifier 本身就是那种局的开局礼物，
`Neow.cs:218` 的 if/else 决定了两者不会同时出现；所以"带 Modifier 的局里哆来咪只给 Modifier 选项"不是妥协，
而是与涅奥同样的行为。另外每日抽到的两个 good modifier 若都不提供涅奥选项（`囤积癖` / `飞行` / `上等好货` /
`角色牌` 里取两个，概率 `4/9 × 3/8 = 1/6`），原版那一页就是空的、只剩「继续」——
`LeaveDreamNeowOptionsPatch`（见 7.15）兜的就是这种空表。

**链为空为什么必须回落到正常选项：第三方"隐形 Modifier"（2026-09-28）**
原版敢在链为空时直接返回空表，是因为原版 Modifier 要么提供涅奥选项、要么本身就是每日挑战的开局礼物，
空页只会出现在上面那 1/6 的每日情况里。但第三方 mod 会往 `RunState.Modifiers` 里塞"纯粹当开关用、
不提供涅奥选项"的 Modifier，最典型的是 **Zone the Spire**（`ZoneTheSpire.dll`，`ZONE_THE_SPIRE_MODIFIER`）：

- 它在 `RunState.CreateForNewRun` 与 `RunState.FromSerializable` 的 Postfix 里调
  `RunModifierInjection.EnsureModifier`，**每一局**（含标准局、含读档）都把自己登记进 `RunState.Modifiers`；
  它是地图改造类的常驻开关，`ZoneConfig` 里也没有总开关。
- 它自己知道这会让涅奥那一页失真，于是只给 `Neow` 打补丁：`Neow.GenerateInitialOptions` 与
  `Neow.InitialDescription` 的 Prefix/Finalizer 调 `HiddenModifier.Hide` / `Restore`（反射
  `<Modifiers>k__BackingField`）把 `ZoneTheSpireModifier` 临时摘出 `RunState.Modifiers`，
  让原版走"没有 modifier"那条岔路；`NTopBar`、自定义/每日读档界面同理（`HideSerialized`）。
- 这些补丁全都写死 `typeof(Neow)`，而本 Mod 的先古之民是另一个类
  （`CustomAncientModel : AncientEventModel`，**不是** `Neow` 的子类），补丁不会命中。
  于是装了 Zone the Spire 以后：`RunState.Modifiers` 恒非空、Modifier 链恒为空 →
  哆来咪的房间恒为"空选项 → `StartPreFinished()`"，整页只剩「继续」，她自己的三个遗物选项、挑战选项与
  「离开梦境」全都不出现，玩家一个遗物都拿不到（涅奥那边因为它的补丁而完全正常，所以只坏本 Mod）。
- 回落只发生在"链为空"这一个原本必然坏掉的分支：只要有任何 Modifier 真的提供涅奥选项，行为与本改动前
  逐字相同，"不会既拿遗物又拿 Modifier"这条原则不受影响。代价是上面那 1/6 的每日局里，原版涅奥给空页、
  而哆来咪会给正常祝福（拿来换"装了这类 mod 就永远没有哆来咪"是不亏的）。
- 同一根因也解释了 7.15 的 `LeaveDreamNeowOptionsPatch`：那个补丁是反过来"临时清空 `RunState.Modifiers`
  让涅奥重掷"，本处则是直接跳过 Modifier 岔路（本 Mod 的正常选项不读 `RunState.Modifiers`，不需要反射）。

### 7.18 召唤多个同名分身：私有集合必须 `AfterCloned` 重建

参考 `SilentObjectMonster`（鬼人正邪「妖器再塑」可同时召出 2 个不语之物）。

- `ToMutable()` 全走 `MemberwiseClone()`（同 7.14 的浅拷贝，见 9.5）：**值类型字段（`int` / `bool`）每个分身各自独立，但引用类型字段（`List<T>` 等）被所有分身 + canonical 共享同一个实例**。
- 后果：分身 A 死亡时 `foreach (node in _cardNodes) node.QueueFreeSafely()` 会把分身 B 正在显示的卡面节点一并摘走归还节点池（`NCard.OnFreedToPool` 还会把立绘贴图置空），表现为"一个不语之物死了，其他不语之物的卡面变空"。
- 修法：字段去掉 `readonly`，在 `protected override void AfterCloned()` 里 `_cardNodes = [];`。
- 只在**同一场战斗里可能出现多个实例**的怪物上才会暴露；单实例怪物（魔理沙等）即使写了同样字段也看不出问题。

### 7.19 Power 文案键 slug 规则 + tooltip 列表占位符（正邪「妖器再塑」）

- **文案键 = `TOUHOUANCIENTS-` + `StringHelper.Slugify(类名)`**，且 slug **不给数字补分隔符**：`SilentObjectCardPower` → `SILENT_OBJECT_CARD_POWER`，`SilentObjectCard2Power` → `SILENT_OBJECT_CARD2_POWER`（不是 `..._CARD_2_POWER`）。同一机制要两套文案不必新建类：`Title` / `Description` / `SmartDescriptionLocKey` 都是虚属性，用实例标志切前缀即可（`SilentObjectCardPower.FromDeck`：牌组移除的牌＝被抛弃者，战斗中因魔力躁动被鼓动的牌＝弱者）。
- **Power tooltip 只能靠 `DynamicVars` 注入占位符**（`PowerModel.HoverTips` 里只做 `DynamicVars.AddTo`，没有卡牌那种 `Description` 覆写点），要写 `{Cards:list:{}|、}` 就得给一个**值为列表的动态变量**：`scripts/CmdUtils/StringListVar.cs`（`DynamicVar` + `IEnumerable<string>`），分隔符留在本地化文本里。
- 用游戏自带的 `SmartFormat.dll` 实测：`list` 格式只要求 `IEnumerable`（只实现 `IEnumerable<string>` 也能用），但**值传字符串会抛 `FormattingException: Formatter named 'list' requires an IEnumerable argument`** —— 没有列表时传空列表，别传 `""`。
- 悬停提示里要显示「某张牌的全部提示」：卡面用 `HoverTipFactory.FromCard(实例)`，其余用 `CardModel.HoverTips`（附魔 / 苦恼 / 关键词 / 重放 / 激发…，手牌里悬停那张牌看到的就是这一组）；实例版比 `FromCardWithCardHoverTips<T>`（canonical + upgrade 开关）更准，能带上附魔与苦恼。参考 `SilentObjectCardPower.ExtraHoverTips`。
- 「妖器再塑」候选消耗：`KijinSeijaMonster._consumedCandidates`（`ReferenceEqualityComparer`；战斗牌按 CardModel 实例、历史牌按 `SerializableCard` 条目）记录已塑成不语之物的候选，整场战斗每个条目只出一次（衍生体死亡把牌还回弃牌堆后也不会再被抓）；天地有用提示里的 `{Cards}` 只列**尚未消耗**的本局被移除基础打击/防御牌。

### 7.20 怪物意图的生成时机与「行动后改判」

参考 `KijinSeijaMonster`（正邪 天壤梦弓 / 逆命诏敕 之后按“场上无不语之物且仍可征招”改判妖器再塑）。

- 意图不是敌方回合才滚的：**玩家回合开始时** `CombatManager` 对每个敌人 `PrepareForNextTurn` → `MonsterModel.RollMove` → `MoveStateMachine.RollMove`（从当前状态沿 `FollowUpState` / 条件分支推进到下一个 `MoveState`）并刷新意图 UI；敌方回合只是执行 `NextMove`。所以玩家在自己回合看到的图标就是本回合末要执行的动作，「上一个意图」＝刚执行完的那个。
- `Hook.BeforeSideTurnStart` 早于这次 Roll（在那里覆盖会被冲掉），`Hook.AfterSideTurnStart` 在它之后。
- 想「某步之后条件成立就改判别的技能、又不打乱原有顺序」：在链上插 `ConditionalBranchState`（`AddState(state, () => 条件)` + 末尾兜底 `() => true`），**不要**去覆盖 `NextMove` —— 它只能经 `SetMoveImmediate` 改，而那是 `NextMove = state` + `ForceCurrentState(state)`，会把状态机当前位置一起挪走。分支的 `GetNextState` 只按顺序求条件、不消耗随机数（多人一致），且 `ShouldAppearInLogs => false` 不进 `StateLog`，所以 `MindProbe` 那套「按 `StateLog` 取下一意图」的眩晕逻辑不受影响。
- **改判后要接回原来被打断的那一步**：给改判目标另建一个 `MoveState`（同一套行动逻辑，`FollowUpState` 指向被打断的下一步），不要复用入口那个。`KijinSeijaMonster` 就是：`FIGHT_FOR_ME`（入口，→ 天壤梦弓）、`FIGHT_FOR_ME2`（→ 逆命诏敕）、`FIGHT_FOR_ME3`（→ 喑哑泣啼）。
- 图鉴会把 `MoveStateMachine.States` 里**所有** `MoveState` 都列进招式表（`GenerateBestiaryMoveList` → `GetAllMoves`），每个都要 `...moves.{id}.title`；**id 以 2/3/4 结尾且没有该键时会被静默跳过**（不 Warn、不列出），所以这种「同名变体」状态直接用 `FIGHT_FOR_ME2` / `FIGHT_FOR_ME3` 命名即可，不必补本地化键。

## 9. 自定义奖励（TouhouCustomReward）与「打出后移出游戏」

### 9.1 基类与注册

- 基类 `scripts/Rewards/TouhouCustomReward.cs`（继承 BaseLib 的 `BaseLib.Abstracts.CustomReward`），命名空间 `TouhouAncients.Scripts.Rewards`。已有实例：`UpgradeCardReward`（选牌升级）、`TranscribeReward`（誊写）、`DreamAwakeningReward`（「梦醒时」梦境牌变化）、`TransformCardReward`（选牌变化，`Amount` 张）。
- 子类必须自带 `[CustomEnum(null)] public static RewardType Xxx;` 字段，并实现 `RewardType`、`DeserializeMethod`（必须是 **static** 方法）、`ToSerializable()`、`MarkContentAsSeen()`、`OnSelect()`；`RewardsSetIndex`、`IsPopulated`、`Populate()`、`Description`、`CreateIcon()` 由基类兜底。
- **不要自己调 `Initialize()`**，也不用改 `Entry.cs`：BaseLib 的 `GenEnumValues`（Harmony prefix `ModelDb.Init`）会枚举所有含 `[CustomEnum]` `RewardType` 字段的 `CustomReward` 子类，**拿未初始化实例调 `ToSerializable()`**（所以该方法不能碰 `Player` 或实例状态），要求返回值既不是 `None` 也不是原版 0~6，然后 `Initialize()` 注册读档工厂（`Reward.FromSerializable` 已被 patch）。
- 描述文本表固定 `gameplay_ui`，Key = `TOUHOUANCIENTS-<类名蛇形大写>`：`UpgradeCardReward` → `TOUHOUANCIENTS-UPGRADE_CARD_REWARD`，`TranscribeReward` → `TOUHOUANCIENTS-TRANSCRIBE_REWARD`，`TransformCardReward` → `TOUHOUANCIENTS-TRANSFORM_CARD_REWARD`。mod 的 `gameplay_ui.json` 只在**原版已有同名文件**时才会被合并，所以文件名必须照原版表名。
- **自定义数据借 `SerializableReward` 的现成字段存**：`GoldAmount`（int）与 `CardPoolIds`（`List<ModelId>`）在存档 JSON 与二进制联机包里都**始终**读写，可以直接拿来存自定义数据 —— `UpgradeCardReward` 用 `GoldAmount` 存张数，`TranscribeReward` 用 `CardPoolIds` 存来源角色卡池 id（该字段读回时按 `CardPoolModel` 校验类型，别塞别的模型 id）。`SpecialCard` 走存档 JSON 能带任意类型，但二进制联机包只在 `RewardType.SpecialCard` 时才写它；`PredeterminedModelId` 虽然也始终读写，但 `Reward.FromSerializable` 只在 `RewardType.Relic` 分支读它。
- 发放：`RewardsCmd.OfferCustom(player, List<Reward>)`（独立界面，事件/遗物拾起）或 `CombatRoom.AddExtraReward(player, reward)`（追加到当前战斗结算奖励，战斗内触发）。`RewardsSet.WithRewardsFromRoom` 在生成奖励时读一次 `ExtraRewards`，所以战斗中随时加都有效。

### 9.2 「看另一个角色牌库选一张但不入手」的标准写法

`CardReward` **不能**用来「只记录不入手」——它的 `OnSelect()` 里硬编码了 `CardPileCmd.Add(card, PileType.Deck)`，返回值只有 bool，拿不到选的是哪张。要自己处理选中的牌就用卡牌选择命令：

```csharp
var options = new CardCreationOptions(
        new[] { ModelDb.CardPool<IroncladCardPool>() },
        CardCreationSource.Other,
        CardRarityOddsType.RegularEncounter)
    .WithFlags(CardCreationFlags.NoCardPoolModifications);   // 防止其他遗物扩大卡池
List<CardCreationResult> list = CardFactory.CreateForReward(player, 3, options).ToList();

// 首选：原版「发现」界面（自带标题与跳过，3 张以内），返回选中的那张或 null
CardModel? picked = await CardSelectCmd.FromChooseACardScreen(
    new BlockingPlayerChoiceContext(), list.Select(o => o.Card).ToList(), player, canSkip: true);

// 备选：网格选择（想自己定表头、或要显示卡牌改动者时）
var prefs = new CardSelectorPrefs(promptLoc, 1, 1) { Cancelable = true };
CardModel? picked2 = (await CardSelectCmd.FromSimpleGridForRewards(
    new BlockingPlayerChoiceContext(), list, player, prefs)).FirstOrDefault();
```

- `FromChooseACardScreen` 内部 `cards.Count > 3` 会抛 `ArgumentException`；`canSkip: true` 才给跳过按钮。

- `CardCreationOptions` 是 `record`，有 `IEnumerable<CardPoolModel>` 与 `IEnumerable<CardModel>` 两个构造；`new[] { pool }` 走前者。
- **选牌提示优先复用原版文本**：`CardSelectorPrefs` 只吃一个 `LocString`，通用表头直接用 `new LocString("gameplay_ui", "CHOOSE_CARD_HEADER")`（zhs「选择一张牌」/ eng「Choose a Card」/ jpn「カードを選択」），不要为此新造 key——原版三语全都有，日语还是真日语，而本 mod 的 `jpn/*.json` 按工作流是拿英文顶的。`card_selection` 表里的 `TO_UPGRADE` / `TO_REMOVE` 等是「选择{Amount}张牌来 <动作>」模板，只有**确实要新增一个动作动词**时才值得照模板补 key。
- `CardSelectorPrefs(prompt, min, max)` 在 `min != max` 时才需要手动确认；`min == max == 1` 是点一下即选中。`FromSimpleGrid*` 在非战斗下可用（只挡 `CombatManager.Instance.IsEnding`）。
- 「该牌属于哪个角色」用卡牌池反查：`ModelDb.GetByIdOrNull<CardModel>(card.Id)!.Pool.Id` 与各角色池 `Id` 比较。

### 9.3 卡牌「打出后移出游戏」/ 本场战斗移除

- 牌组里的牌每场战斗都被 `Player.PopulateCombatState()` **克隆**进抽牌堆（`DeckVersion` 指回牌组原件），所以「本场战斗移出游戏」只处理战斗副本：`CardPileCmd.RemoveFromCombat(card, skipVisuals)`，牌组原件不受影响，下场战斗照常出现。`PileType.None`（内部叫 Limbo）**没有牌堆对象**，不能 `CardPileCmd.Add(card, PileType.None)`。
- 卡牌自身打出后的去向覆写**当前版本**的 `protected override CardLocation GetResultLocationForCardPlay()`，返回 `new CardLocation(Owner, PileType.None, CardPilePosition.None)` 即移出游戏。（旧版的 `GetResultPileType()` / `GetResultPileTypeForCardPlay()` 在安装版里**已不存在**。）
- **注意时序**：`GetResultLocationForCardPlay()` 在 `OnPlay` **之前**求值。依赖"打完之后的场面"时要提前算——百鬼夜行用的是等价判据「打出前记录池 ≤ 本次消耗张数 ⇒ 打出后必为空」。
- 在 `OnPlay` 里对**正在打出的这张牌**调 `RemoveFromCombat` 会动到出牌队列节点；让引擎按 result location 处理更稳。战斗开始阶段对还在战斗牌堆里的牌调 `RemoveFromCombat` 是安全的（百鬼夜行就是在 `BeforeCombatStart` 里把自己移出游戏的）。`RemoveFromCombat` 要求卡牌确实在战斗牌堆（`Pile.IsCombatPile`），否则抛 `InvalidOperationException`。
- 让「生成的临时牌」打完就消失：`CombatState.CreateCard(...)` 造副本 → `CardCmd.AutoPlay(ctx, card, target: null)`（`target: null` 自动随机敌人）→ 打完 `if (card.Pile is { IsCombatPile: true }) CardPileCmd.RemoveFromCombat(card, skipVisuals: true)`。

### 9.4 遗物选项池最后一个实参后面**不能有逗号**

`MakeOptionPools`（BaseLib 路线：`MakePool` + `AncientOption<T>`）与本仓自己的 `TARelicOptionPools`（`CreateTARelicOptionPool` + `TARelicOption<T>`）都是 `params`，参数表末尾的 `,` 后面直接接 `)` 是语法错误。注释掉最后一项时要把逗号一起处理：

```csharp
TARelicOption<HeavyDice>(),
//TARelicOption<OneEyedKarakasa>(),
TARelicOption<HyakkiYagyoScroll>()     // ← 最后一项不加逗号
//TARelicOption<NohMask>()
```

报错是 `CS1525 表达式项")"无效`，列号指向该项的 `)` 之后，很容易被误判成泛型解析问题。

### 9.5 「誊写 / 百鬼夜行绘卷」参考实现

- **记录在卡牌上，遗物只发奖励**：`scripts/cards/HyakkiYagyo.cs` 用 `[SavedProperty] private List<SerializableCard> HyakkiYagyo_Records` 存誊写记录（`List<SerializableCard>` 是 `SavedProperty` 支持的类型，存成 `cardArrays`），并自己管理本场战斗的记录池；`scripts/relics/Mamizou/HyakkiYagyoScroll.cs` 只做 `AfterObtained()`（`CardPileCmd.Add(RunState.CreateCard<HyakkiYagyo>(player), PileType.Deck)` + `RewardsCmd.OfferCustom` 五个角色的誊写奖励）与 `AfterDeath()`（`creature.IsEnemy` + `Powers.All(p => p.ShouldOwnerDeathTriggerFatal())` 判斩杀后 `CombatRoom.AddExtraReward`）。BaseLib 会自动为含 `[SavedProperty]` 的 mod 类型调 `SavedPropertiesTypeCache.InjectTypeIntoCache`，不必改 `Entry.cs`。
- 誊写写入由 `scripts/Rewards/TranscribeReward.cs` 负责，**按角色卡牌池（`CardPoolModel`）而非固定角色名单**工作：选择时取 `PileType.Deck.GetPile(Player).Cards.OfType<HyakkiYagyo>()`，对牌组里**每一张**各写一份记录（多张百鬼夜行各自持有一份，互不共享）；记录按卡池 id 去重，即"每种角色最多一张"。角色来源只有两处：`HyakkiYagyoScroll.AfterObtained` 固定 Ironclad / Silent / Regent / Necrobinder / Defect 五个池，`AfterDeath` 从 `player.UnlockState.CharacterCardPools` 里排除玩家自己的池后随机一个（与原版 `Kaleidoscope` 取"其他角色池"的写法一致）。奖励读档用 `SerializableReward.CardPoolIds` 存来源池 id，角色显示名按卡池反查 `ModelDb.AllCharacters`。
- **战斗副本与牌组原件的钩子关系**（决定了这类卡怎么写）：`RunState.IterateHookListeners()` 会把**牌组原件**（`player.Deck.Cards`）和**战斗副本**（`CombatState` 各战斗牌堆里的牌）都列为监听者，所以 `BeforeCombatStart`/`AfterCombatEnd` 两边都会收到 —— 卡牌侧要用 `Pile is { IsCombatPile: true }` 区分，牌组原件什么都不做。
- **本场记录池的播种**：`Player.PopulateCombatState()` 走 `PlayerCombatState.DrawPile.AddInternal(...)`，**不会**触发 `AfterCardEnteredCombat`（该钩子只在 `CardPileCmd` 从「原本不在任何牌堆」加入战斗牌堆时触发），所以战斗开始必须在 `BeforeCombatStart` 里从牌组原件复制记录池；`AfterCardEnteredCombat` 只负责战斗中才出现的副本（例如复制出来的牌）。
- **克隆是浅拷贝字段**：`AbstractModel.MutableClone()` = `MemberwiseClone()` + `DeepCloneFields()` + `AfterCloned()`，副本与原件共享同一个 `List` 实例，所以本场记录池要在 `AfterCloned()` 里换成新的一份。持久记录反过来可以利用这一点：副本读 `DeckVersion` 指向的牌组原件那份。
- 记录池为空时只把**这张牌自己**移出游戏，不去动同名的其他副本（多张百鬼夜行互相独立）。
- 斩杀判定沿用本 mod `HellOrin` 的约定，即**按"敌人死亡"计**，毒杀/敌人互杀也算；要严格「你亲手斩杀」需改用 `AfterDamageGiven` + `dealer == Owner.Creature` + `DamageResult.WasTargetKilled`。
- 选誊写目标用 `CardSelectCmd.FromChooseACardScreen(new BlockingPlayerChoiceContext(), candidates, Player, canSkip: true)`（原版 `Toolbox` / 各药水的「发现」界面），**不要**用 `FromSimpleGridForRewards` 网格：那要自己造 `CardSelectorPrefs` 与表头，而这个界面自带标题与跳过按钮，选完即返回选中的那张。取牌：`CardFactory.CreateForReward(...)` 的结果转 `options.Select(o => o.Card)`。该方法只接受 **3 张以内**，超过会抛。
- **「已誊写」悬停挂在卡牌自己的 `ExtraHoverTips` 上**（`HyakkiYagyo`），不挂在遗物上：getter 里先取记录，空就直接 `return []`（不显示空条目），有记录才返回 `HoverTip(title, description)` + 每张牌的 `HoverTipFactory.FromCard(model, upgraded)` 卡面（能传 `upgraded` 的是非泛型重载）。文字用 `LocString` + `description.Add("Cards", 卡名 List<string>)`，列表格式写在本地化文本里（`{Cards:list:{}|，}` / eng `{Cards:list:{}|, }`），分隔符因此各语言自己决定，不要在 C# 里硬编码（同 `BrainInAVat`）。
- **持久记录在牌组那张牌上，不在 `ModelDb.Card<T>()` 的 canonical 上**：`RunState.CreateCard` 是 `canonical.ToMutable()`，牌组里的是那个 mutable 实例，所以卡牌自己读记录要认准持有者 —— `RecordOwner`（战斗副本走 `DeckVersion` 指回牌组原件）；canonical（图鉴）自己没有记录，只能退回 `Owner?.Deck.Cards` 里找那张牌，找不到就不显示。

### 9.6 休息处「当你休息时」的触发与变化奖励

- **卡牌也能改休息处**：`TryModifyRestSiteOptions`（加按钮）、`AfterRestSiteHeal`、`TryModifyRestSiteHealRewards`、`ModifyExtraRestSiteHealText` 全都定义在 `AbstractModel` 上，而 `RunState.IterateHookListeners()` 会遍历 `player.Deck.Cards` —— 牌组里的卡牌就是 run-state 监听者，所以卡牌能接这些钩子。多人下每个钩子都会为**每个玩家**各遍历一次，「玩家」只用来判 `player != base.Owner` 早退。参考实现：`DreamCycleCard` + `DreamAwakeningReward`。
- **「选择休息（HEAL）」的流程**：`HealRestSiteOption.ExecuteRestSiteHeal` → `CreatureCmd.Heal` → `await Hook.AfterRestSiteHeal(...)` → `Hook.ModifyRestSiteHealRewards(...)` → `RewardsCmd.OfferCustom(player, rewards)`。由此：
  - 想**弹交互界面**（要 await）用 `AfterRestSiteHeal(Player, bool isMimicked)`（`Task`，会被 await）。
  - 想**追加一条奖励**（小邮箱 `TinyMailbox` / 捕梦网 `DreamCatcher` 同款）用 `TryModifyRestSiteHealRewards(Player, List<Reward>, bool isMimicked)`（同步 `bool`，只能 `rewards.Add(...)`）。
  - 「锻造」不在这里，是另一个钩子 `AfterRestSiteSmith`。
- **`isMimicked`**：原版事件 `DenseVegetation` 的 Rest 选项走 `PlayerCmd.MimicRestSiteHeal`，也会触发这两个钩子。算不算「休息」由内容自己定（`DreamCycleCard` 选择不算）。
- **「可以」= 可跳过**：`CardSelectCmd.FromChooseACardScreen(new BlockingPlayerChoiceContext(), cards, player, canSkip: true)` 返回选中的牌或 `null`（原版 `Toolbox` / `MassiveScroll` / 各药水用同一个界面）。`BlockingPlayerChoiceContext` 是原版给非战斗与遗物回调场景准备的上下文（`SignalPlayerChoice*` 是空实现，remote 同步仍走 `PlayerChoiceSynchronizer`）。网格版是 `FromSimpleGrid`。
- **衍生牌的临时关键词/费用**：`CardPileCmd.AddGeneratedCardsToCombat(...)` 返回结果集，对 `result.cardAdded` 可 `AddKeyword(...)`；「直到打出」的费用 -1 用 `cardAdded.EnergyCost.AddUntilPlayed(-1)`（「梦色」附魔同款），打出的瞬间自动清除。参考 `DreamCycleCard.AddRandomDreamCards`。
- **变化并继承升级/附魔**：`CardCmd.Transform` **不会**继承（`CardFactory.CreateRandomCardForTransform` 只造一张新牌），要照原版 `Claws`（利爪→撕咬）自己搬：

```csharp
var to = player.RunState.CreateCard(ModelDb.Card<Maul>(), player);  // mutable 实例；owner 不一致 Transform 会抛
if (from.IsUpgraded && to.IsUpgradable) CardCmd.Upgrade(to);         // 不在牌堆时 Upgrade 不放 VFX、不写历史
if (from.Enchantment != null)
{
    var e = (EnchantmentModel)from.Enchantment.MutableClone();        // 活的附魔得用 MutableClone；ToMutable() 只接受 canonical
    if (e.CanEnchant(to)) CardCmd.Enchant(e, to, e.Amount);          // CanEnchant 为 false 必须跳过，否则 CardCmd.Enchant 抛异常
}
await CardCmd.Transform(from, to);
```

  `CardTransformation(original, replacement)` 显式替换不需要 RNG。`CardCmd.Transform` 对 `PileType.Deck` 有专门分支，脱离战斗改牌组是支持的（原版 `Astrolabe` 就是这么回事）。先给候选继承再放入选择界面，玩家看到的就是变化后的实际结果。
- **奖励要指向「具体哪张牌」时的存档办法**：奖励里可以存牌实例，但读档后实例不存在了 —— `SerializableReward` 没有能安全存 `ModelId` 的字段（`GoldAmount` 是 int、`CardPoolIds` 会被当卡池类型校验、`SpecialCard` 在二进制联机包里只在 `RewardType.SpecialCard` 时写）。做法是**用 `GoldAmount` 存一个序号**（如「哪一张梦境牌」），读档后按序号在 `player.Deck.Cards` 里找同名牌，正常流程仍优先用内存实例。

### 9.7 反编译源码可能是过期版本，别照它写代码

§3.2 让查反编译源码的 `src\Core` / `localization`，但手边那份可能是 2026-04-30 的旧 build，与安装版差异很大（本机有哪几份、哪份过期见 `.agents/local.md`）：

| | 旧 build（反编译源码） | 安装版 |
|---|---|---|
| `Reward.Populate()` | `Task` | `void` |
| 卡牌结果牌堆 | `CardModel.GetResultPileType()` | `CardModel.GetResultLocationForCardPlay()` → `CardLocation` |
| 命名空间 | — | 多了 `CardLocation` / `ModifyCardPlayResultLocation`，没有 `ModifyCardPlayResultPileTypeAndPosition` |

**查 API 的优先顺序**：① 随游戏分发的 `data_sts2_windows_x86_64\sts2.xml`（约 5.6 MB 的官方 API 文档，含每个成员的签名与注释）；② 手边那份反编译源码（本机是哪份见 `.agents/local.md`）；③ 本仓里能编译的同类实现；④ 以上都不够时以**编译器**为准。

`Sts2Dir`（csproj 里的属性，本机取值见 `.agents/local.md`）指向的才是真正被引用的 `sts2.dll`。命令行覆盖即可编译，不必改 csproj：

```powershell
dotnet build <csproj> -p:Sts2Dir="<你的安装目录>"
```

Godot.NET.Sdk 会把 `obj/bin` 放到 `$(GodotProjectDir).godot\mono\temp\`，另有 `Copy Mod` 目标在 PostBuild 复制到游戏目录；想只验证编译可以用 `-p:BaseIntermediateOutputPath` / `-p:OutputPath` 重定向到仓外目录。
